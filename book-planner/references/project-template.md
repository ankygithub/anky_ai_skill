**注意**：信息来源列直接写入调研资料的核心结论摘要，不要只写文件路径。PROJECT.md 应是完整自包含文档，读者无需跳转到其他文件即可理解上下文。

**类型标签**：[概念] [实操] [案例] [练习] [反思] [故事] [对比] [拓展]

**需要采集**：标记该章节是否需要写书技能在写作前额外搜索素材。`是`=需要补充搜索，`否`=现有调研资料已充分。

**采集方向**：仅"需要采集"=是时填写。给写作 agent 提供搜索线索，写得越具体越好。

### 采集判断指南

以类型标签为主线索，按以下规则判断：

| 类型标签 | 通常是否采集 | 原因 |
|---------|------------|------|
| [案例] | **是** | 需要真实事件、具体数据、时间线，模型内置知识容易编造 |
| [实操] | **是** | 需要真实的操作步骤、配置示例、踩坑经验 |
| [练习] | **是** | 需要真实题目或场景，避免虚构 |
| [对比] | **是** | 需要真实的对比数据和评测结果 |
| [概念] | 否 | 模型知识足够，无需额外搜索 |
| [反思] | 否 | 观点性内容，模型知识足够 |
| [故事] | 看情况 | 有真实故事原型则采集，纯虚构场景则否 |
| [拓展] | 看情况 | 涉及最新技术/趋势则采集，否则否 |

**自检问题**（做判断时逐条自问）：
1. "这一章如果只靠内置知识，案例会不会是编的？" → 会 → 标`是`
2. "这一章需要的数据/配置/命令是最新版本的吗？" → 是 → 标`是`
3. "这一章的核心价值是传递概念/观点吗？" → 是 → 标`否`

**采集方向的写法要求**：
- 写给写作 agent 看的搜索提示，不是给读者看的
- 越具体越好：写"搜 Kubernetes OOMKilled 排查的生产案例"，不要写"搜 K8s 相关资料"
- 可以包含具体关键词建议

**要求**：
- 每章必须有明确的核心内容
- 每章必须能回答一个读者问题
- 不允许"概述""介绍"等弱标题
- 信息来源必须写入具体结论摘要
- 资料不足标注"待补充"

**SVG 绘图规划**：
本书涉及图解时优先使用 SVG 格式。规划阶段需标注每个图表的 SVG 实现方案：
- 简单图表（坐标系、函数图像、对比图）：直接输出 SVG 代码
- 复杂图表（流程图、关系图、韦恩图）：描述 SVG 结构，由写作阶段实现
- SVG 文件命名规则：`assets/fig-{章节号}-{图表描述}.svg`
- 在章节规划中标注"建议SVG"或"建议ASCII"
