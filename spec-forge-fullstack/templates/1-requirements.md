# 模板：1-需求分析（需求文档的根，必产）

> 使用说明：`docs/1-需求分析.md`。全组的根节点——给 AI 看的文档里每条需求、每条验收标准都从这里来，**任何项目不可省**。利益相关者识别、MoSCoW 优先级、大功能→模块→REQ 三层组织、P0 级 GWT 前移。需求调研时的决策（D-x）并入 §10，不单独成文。叙述遵守 `_writing-guide.md`（`templates/_writing-guide.md`）。
>
> **v2.0 两条硬要求**：① **每条需求都要标条目类型**（定义 / 约束 / 流程 / 判定 / 计算 / 推导），类型决定后面概设、详设要展开到什么精度；② **每条需求都要能回答"验收怎么判"**——判不出来的，不硬写，降级为 TBD 标"需求未定"，并在原地留下"因需求未定，本期暂不做"，供后续各级承接。
>
> 红线：只描述"做什么"，不指定"怎么做"——选型理由归 `2-概要设计.md`。状态流转：草稿 → 已冻结（确认点 1）。
>
> **依据标注图例（全库权威，四选一，写在论断后）**：每一条事实论断必须挂一个依据标注，供下游对账与审核判断可信度：
> - `[有据]` 有可查证的来源（公式、文档、实测数据、已确认的原型）；
> - `[调研]` 经由调研推得，但未获权威证实（行业惯例、竞品观察）；
> - `[经验]` 凭过往工程/业务经验推断，没有硬数据；
> - `[假设]` 纯属合理假定，**必须进 TBD（性质标"已假设"），冻结前需用户确认或反驳**。
>
> 已经在用的标注一律按此图例解释，不另立新词。

## 4. 功能需求

> 优先级用 MoSCoW，映射写死：Must→P0 / Should→P1 / Could→P2 / Won't→§7 排除候选。按"大功能→模块→REQ"三层组织，简单项目 REQ 平铺。**P0 条目必须附 GWT 三行**（给 AI 看的验收标准的生成素材）。
>
> **条目类型（必填，六选一）**：定义类（术语/字段/口径）｜约束类（必须/禁止）｜流程类（顺序/状态迁移）｜判定类（当…且…时做…）｜计算类（公式/阈值/档位/区间）｜推导类（由已有数据推出结论）。后三类是"要逐条判定执行"的条目，**设计侧必须展开到五要素**（见 §5），因此在这里就要把边界与例外问到，问不到的记 TBD。
>
> **可验收性**：每条需求写不出"一句话验收"的，不硬编——转 §12 TBD 标"需求未定"，并在需求描述里写明"因需求未定，本期暂不做"。
>
> **实现现状列**（**据代码回溯/基线重建场景必填**，见 SKILL §9.4）：已实现 / 部分实现 / 未实现，并简述落点（模块/文件）。回溯生成的文档若不标这一列，读者会误以为"没做"，实际早已实现到很细。新建项目（尚未写代码）统一填"未实现"即可。
>
> ⚠️ GWT 三行是**草案**：验收标准定稿时若与之不一致，在确认点 1 摘要里说明。

| 编号 | 需求描述 | 条目类型 | 优先级 | 实现现状 | 一句话验收 | 场景来源 | 来源/依据 |
|---|---|---|---|---|---|---|---|
| REQ-F-1.1 | （主语+动作+对象+边界） | 判定类 | P0 | 未实现 / 已实现（落点） | | SC-x | 分支B填原文章节，分支A填访谈轮次 |

## 5. 业务规则（BR 草稿，正式条目随 spec.md 冻结）

> 业务规则是"超 30 天不可退款""同一手机日限 3 单"这类硬性约束，最需要人眼过目。此处先列草稿，确认点 2 时正式编号进 spec.md §7。用户从未在给人看的文档里见过这些规则前，spec 不得冻结。
>
> **每条规则必须标条目类型**（定义 / 约束 / 流程 / 判定 / 计算 / 推导）。判定类、计算类、推导类是"要按条判定执行"的条目，**在需求阶段就要把边界与例外问到**——设计阶段只做承接与展开，不能指望它凭空补齐业务判据。问不到的记 TBD 标"需求未定"，并写明"因需求未定，本期暂不做"。
>
> **验收方向**：判定 / 计算 / 推导类每条都要能写出"什么情况该命中"和"什么情况不该命中"（反例），写不出的说明规则还没想清。

## 13. 需求对抗性审查结论（确认点 0 前逐条过，必填）

> 需求里的模糊、冲突、漏边界，会一路遗传到概设、详设、验收——到那时再发现，返工代价是这里的十倍。**确认点 0 前逐条过下表，逐条写结论**；不合格项的处置方式必须落地（补边界 / 补反例 / 定取舍并记 D-x / 降级 TBD 标"需求未定"）。
