# 模板：轮次讨论稿（产出 `docs/changes/round-NN/discuss.md`）

> 使用说明：一轮追加需求的**讨论过程**全部落在本文件——用户与 AI 的多轮讨论、**中立评审**、参考素材引用、被否决的想法。**允许脏、允许反复改**，它是过程记录，不是执行依据。用户确认最终结论后**冻结**，据此机械提炼出干净的 `todolist.md`。
>
> **为什么必须有它**：多轮讨论里 AI 会丢上下文；过程落盘，才能避免"讨论过又忘了""同一件事反复推翻""用户的想法其实代码早就实现得更好"。叙述遵守 `_writing-guide.md`（`templates/_writing-guide.md`）。

## 0. 轮次分级与开工门禁（先读这一段）

### 0.1 轮次分级（开工前先判级；决定"设计深度写在哪"）

> **两类变更的差别不在内容多少，而在"设计决策在哪里产生"**：L1 的需求表述里已隐含唯一解（转录即可）；L2 的需求只给约束与目标，**方案本身是设计产物**，必须在这里和你定，不能留给执行 AI 在 `todolist.md` 里替你拍板。
>
> **判定口径（复用详设模板 §1.5 的硬门槛，不另造一套）**：命中任一即为 **L2**——
> ① 状态机 / 多步流转；② 并发 / 去重 / 幂等 / 重试；③ 算法（匹配、排序、提取、解析、压缩、加密、批量或流式）；④ 边界与容错（大文件、超时、部分失败、脏数据）；⑤ 性能门槛（大数据量、内存 / IO 受限）；⑥ 跨层调用链；⑦ **替换或重构既有技术机制**（技术底座、引擎、调度、协议、存储方案）。
>
> 全部不命中 → **L1**（可枚举的确定性变更：加按钮 / 加接口 / 加字段 / CRUD / 改文案）。
>
> **没判级不得开始讨论**；判级结论写在下面这张表里。

| 项 | 填写 |
|---|---|
| 轮次级别 | L1 / L2 |
| 判定依据 | 命中详设 §1.5 第 __ 条（L1 写"第 ①–⑦ 条均不命中"） |
| 涉及的既有机制（L2 必填） | 例：规则引擎 A 设计 → B 设计 |

**级别决定深度归属**：L1 **豁免** §3.2 方案设计整节；L2 **必填** §3.2，且 `AD-{r}.{n}` 的唯一家在那里。

### 0.2 开工门禁

> **本稿是过程记录，不是执行依据**——只负责"把事讨论清楚"，不承担"照着做"。
>
> **禁止据此直接写代码。** 本轮开工的前提是：同目录 `todolist.md` 已从本稿 §6 结论提炼并冻结。
>
> 开工前**必须执行一个预检**（不是"自觉别违反"，是真的做一步并给结果）：
>
> 1. 看同目录有没有 `todolist.md`、状态是否"已冻结"；
> 2. **有** → 按 `todolist.md` 执行，本稿仅作背景（被否决项、讨论过程都不是任务）；
> 3. **没有** → **先停下来产出 `todolist.md` + `test-plan.md`**，再开工；
> 4. **确属微改要免清单** → 必须在 §6 显式写明"本轮微改，免 todolist/test-plan + 理由"，**禁止静默跳过**。
>
> 判定口径：**本轮"开工" = 第一次写下生产代码**。在那之前，`todolist.md` 必须已存在；否则即为违规返工。

## 3. 中立评审与方案设计（动代码前必做；架构类 =【强制】前置闸门）

### 3.1 分轨与中立评审三问

> **制度价值**：用户一句话要求往往不如现状。改之前先让 AI 审查**现状代码 / 现状设计**，回答"该不该改、会不会越改越差、有没有更优方案"。评述原文记在这里，别只留结论。
>
> **先分轨，再评审**（AI 先给每条需求标类型）：
> - **界面 / 交互类调整** → 以**用户为准**，直接执行，不做技术评审（界面好不好用户说了算）。本类只记一句"用户主张，无异议"。
> - **后台 / 架构类优化** → 【强制】中立评审，逐条回答**三问**：① 现状**是否已实现**这个需求（实现了就写"无需改动"）？② 现状**是否比用户要求更优**（若更优，**必须**写"不建议改"并给理由——**不许顺着用户附和**）？③ 有没有**第三条更优方案**？AI 必须站中立客观立场。
>
> **前置闸门**：本轮只要有架构类需求，三问未答完、或未得出"改 / 不改 / 换方案"结论，**不得进入 `todolist.md` 冻结**。

| # | 需求点 | 类型（界面 / 架构） | 现状是什么 | 三问结论（已实现? / 现状更优? / 更优方案?） | 裁定（改 / 不改 / 换方案） |
|---|---|---|---|---|---|
| 1 | | | | | |

### 3.2 方案设计（L2 必填；`AD-{r}.{n}` 的唯一家；L1 整节跳过）

> **为什么必须在这里定**：L2 的需求只给约束与目标（"规则引擎换成 B 设计、要能热更新、要可回溯"），方案是**设计产物**。在这里定不下来，就等于让执行 AI 在 `todolist.md` 里独自发明技术方案——你既没评审过，也无法在事后判断对错。
>
> **深度要求**：够判断"方案对不对"即可，**不要求写代码、不要求精确到行**。必须齐这六项：候选方案 ≥2（确无第二方案时写"唯一可行方案 + 理由"，修 bug 类适用）→ 取舍依据（性能 / 复杂度 / 可维护 / 风险，写明**否决了什么、为什么**）→ 选定 → 关键结构 → 参数初值 → 失败与回滚。
>
> **编号**：`AD-{r}.{n}`（r = 轮次序号）。**定义只在本节**；`todolist.md` 只引用编号、不重写论证。执行中发现方案要改 → 回本节补充并**升版**，不许在清单里就地改。

| 编号 | 决策 | 候选方案（≥2，或"唯一方案 + 理由"） | 取舍依据（为什么选它 / 否决了什么） | 结论 |
|---|---|---|---|---|
| AD-1.1 | 例：规则引擎由 A 设计改为 B 设计 | A 现状 / B1 / B2 | | 选 B1 |
