第十二章 智能客服——系统整体架构

从多平台聚合到智能路由——构建可扩展、高可用、低延迟的AI客服架构

4.5.1 多平台聚合架构概述

2026年的电商企业通常需要在多个平台上提供服务（自有App、网站、微信公众号、小程序、企业微信、电话等）。智能客服系统必须支持多平台聚合——即通过统一的后端架构，为所有前端渠道提供一致的AI服务能力。

多平台聚合架构 的核心设计原则是：
  1. 渠道接入层与业务逻辑层分离：各渠道通过标准API接入，核心业务逻辑与渠道无关
  2. 统一会话管理：跨渠道的会话状态统一管理，支持会话迁移
  3. 统一AI能力中台：意图识别、知识检索、对话管理等AI能力集中管理
  4. 统一业务对接：通过业务网关统一对接各业务系统

4.5.3 会话管理三大特性详解

特性一：跨平台会话合并

用户在多个渠道之间的切换是常态（如：先在网页咨询，再通过小程序继续）。跨平台会话合并确保用户在不同渠道之间切换时，AI能够无缝衔接上下文。

实现方案：
方案适用场景技术方案优缺点
用户ID关联已登录用户通过用户ID关联跨渠道会话准确度高，但未登录用户无法关联
设备指纹关联未登录用户通过浏览器指纹/设备ID关联覆盖未登录场景，但存在误关联风险
手机号关联用户主动提供通过手机号关联历史会话准确度高，但需要用户主动提供

特性二：上下文持久化

智能客服需要记住对话上下文，才能支持多轮对话和话题回归。上下文持久化的核心是结构化存储会话状态。

上下文存储策略：
数据类型存储介质TTL说明
活跃会话上下文Redis30分钟正在进行的会话，需要极速读写
历史会话记录MongoDB永久完整会话记录，用于回溯和分析
用户画像Redis + MySQL永久用户基本信息+行为标签
对话摘要MongoDB永久每轮对话的结构化摘要
业务状态Redis24小时当前业务操作状态（如：正在办理退款）

路由引擎的设计原则：规则优先，模型辅助。简单场景用规则快速路由，复杂场景用模型判断。规则的优先级高于模型，确保关键场景（如投诉、高价值订单）的处理可控。

4.5.4 系统分层职责

层级核心职责关键指标技术选型建议
接入层消息接收、协议转换、限流消息接收延迟 <50msNginx + API Gateway
会话层会话管理、上下文存储、智能路由上下文读取延迟 <10msRedis + MongoDB
AI能力层意图识别、知识检索、答案生成意图识别延迟 <200msBERT/LLM + Milvus
业务服务层工单、知识管理、质检、数据分析服务响应延迟 <500msSpring Cloud / Go
业务网关层业务系统对接、数据转换、容错接口成功率 >99.9%API Gateway + 熔断器

4.5.5 架构设计关键决策

决策一：单体 vs 微服务

方案适用场景优点缺点
单体架构小型项目、POC阶段开发简单、部署方便扩展性差、耦合度高
微服务架构中大型项目、多团队独立部署、弹性伸缩、技术异构运维复杂、分布式问题排查困难
模块化单体中型项目、单一团队模块解耦、开发效率高扩展性介于两者之间

建议：POC阶段使用模块化单体，验证通过后逐步拆分为微服务。不要一开始就上微服务，避免过度设计。

决策二：同步 vs 异步处理

操作类型处理方式理由
意图识别同步用户等待响应，延迟敏感
知识检索同步用户等待响应，延迟敏感
答案生成流式输出（SSE）长文本需要渐进展示
业务API调用同步/异步查询类同步，操作类异步
工单创建异步无需即时返回结果
质检分析异步后台处理，不影响用户体验
数据汇总异步定时任务，离线处理

决策三：自研 vs 采购

模块建议理由
意图识别模型采购/开源+微调模型训练门槛高，开源基座+业务数据微调性价比最高
RAG引擎自研+开源组件核心业务逻辑，需要深度定制
会话管理自研与业务强耦合，难以标准化
工单系统采购/开源标准化程度高，自研性价比低
质检系统自研+AI能力需要与业务规则深度结合

4.5.6 本章小结

智能客服的系统架构是一个多层级、多组件协作的复杂系统。多平台聚合架构确保了跨渠道的一致性体验，会话管理的三大特性（跨平台合并、上下文持久化、智能路由）是架构设计的核心。在架构决策上，应遵循"简单优先、渐进式演进"的原则，避免过度设计。下一章将深入AI能力模块的技术细节。
