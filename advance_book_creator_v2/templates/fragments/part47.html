第四十七章 文档与合同智能处理——证据链与人工复核

8.3 证据链要求与人工复核机制

文档与合同智能处理系统的输出结果在法律、审计、金融等场景中具有严肃的效力要求。AI系统不能仅给出一个结论，必须提供完整的证据链，让审查者能够追溯到原始依据。这是系统从"辅助工具"走向"可信系统"的关键门槛。

8.3.1 证据链的核心要求

AI说某条款有风险，不能只给一句"该条款存在法律风险"。完整的证据链必须包含以下四个要素：

要素说明示例
原文位置风险条款在原文中的具体位置第3条第2款，第5页
风险规则触发风险判断的具体规则违约金比例超过LPR的4倍
历史案例类似风险在历史审查中的处理记录2024-06-15审查的类似案件已要求修改
企业规范企业的内部合规标准《集团合同审查规范》第12条规定
原文位置追溯

原文位置追溯是证据链的基础。系统必须能够将AI的判断结果精确映射到原文的具体位置。实现方式包括：

  • 字符级坐标：记录文本在文档中的起始字符位置和长度
  • 段落级坐标：记录文本所在的页码、段落编号
  • 视觉坐标：记录文本在文档图像中的像素坐标（适用于扫描件）
class EvidenceChain:
    """证据链数据结构"""
    
    risk_type: str           # 风险类型
    risk_description: str    # 风险描述
    source_location: dict    # 原文位置
    risk_rule: str           # 风险规则
    confidence: float        # 置信度
    historical_cases: list   # 历史案例
    enterprise_standard: str # 企业规范

class SourceLocation:
    """原文位置"""
    
    page_number: int         # 页码
    paragraph_index: int     # 段落序号
    char_start: int          # 起始字符位置
    char_end: int            # 结束字符位置
    text_snippet: str        # 原文片段
    bounding_box: dict       # 视觉坐标（扫描件）
风险规则说明

风险规则必须具体、可验证。系统不能使用模糊表述，必须明确指出触发风险判断的具体依据：

❌ 不可接受的表述
"该合同条款存在法律风险，建议修改。"
✅ 可接受的表述
"第8条第3款约定'违约金为合同总金额的50%'，根据《民法典》第585条及相关司法解释，违约金超过实际损失30%或超过LPR的4倍时，法院可能认定为过高而予以调整。建议将违约金比例调整为不超过合同总金额的20%。"
历史案例引用

系统应引用企业历史审查中的类似案例，帮助审查者判断：

  • 该类型风险在历史上出现的频率
  • 历史上对该类风险的处理方式
  • 修改后的条款是否最终被对方接受

历史案例的引用需要建立在企业文档结构化数据库的基础上，通过条款相似度匹配实现。

企业规范对照

不同企业的合规标准存在差异。系统必须能够对照企业的内部规范进行判断：

  • 《集团合同审查规范》中的强制性条款
  • 各业务线的特殊合规要求
  • 行业监管规定的具体要求

8.3.2 低置信度字段处理

在文档处理过程中，系统对每个抽取字段都会给出一个置信度评分。置信度反映了系统对该字段识别结果的确定程度。

置信度分级
置信度区间级别处理方式
0.90 - 1.00高置信度自动通过，直接进入结构化输出
0.70 - 0.89中置信度系统推荐结果，标记为"建议采纳"
0.50 - 0.69低置信度进入人工复核队列，需要人工确认
0.00 - 0.49极低置信度标记为"无法识别"，必须由人工录入
低置信度复核队列

低置信度字段自动进入人工复核队列。复核队列的设计应考虑以下要素：

  1. 优先级排序：根据字段重要性排序复核任务。例如，合同金额和违约金的复核优先级高于联系人电话。
  2. 上下文呈现：在复核界面中，不仅展示AI的抽取结果，还要展示原文上下文和原文截图，方便复核人员快速判断。
  3. 一键确认/修正：复核人员应能通过简单的操作确认或修正AI的结果，减少操作负担。
  4. 批量处理：支持同类型字段的批量复核，提高效率。
class ReviewQueue:
    """低置信度复核队列"""
    
    def enqueue(self, field: ExtractedField):
        """将低置信度字段加入复核队列"""
        if field.confidence < self.low_confidence_threshold:
            task = ReviewTask(
                field=field,
                priority=self.calculate_priority(field),
                original_document=self.get_context(field),
                ai_result=field.value,
                confidence=field.confidence,
                status="pending"
            )
            self.queue.push(task)
    
    def calculate_priority(self, field: ExtractedField) -> int:
        """根据字段类型计算复核优先级"""
        priority_map = {
            "contract_amount": 10,      # 合同金额 - 最高优先级
            "payment_terms": 9,
            "violation_liability": 8,
            "party_name": 7,
            "contact_phone": 3,         # 联系电话 - 低优先级
        }
        return priority_map.get(field.field_type, 5)

8.3.3 复核结果反哺标注数据

人工复核的结果是宝贵的标注数据。系统应建立闭环的数据优化机制：

数据回流流程
人工复核
→
结果确认
→
标注入库
→
模型微调
→
效果验证
→
模型上线
标注数据管理
要素说明
标注格式统一采用JSON格式，包含原文、字段名、AI结果、人工修正结果、置信度
标注版本每次模型更新后，标注数据版本号递增，便于追溯
质量校验标注数据需经过二次审核，确保标注准确性
数据隔离不同行业、不同文档类型的标注数据分类存储
持续优化机制
  • 每周统计低置信度字段的类型分布，识别系统薄弱环节
  • 每月使用新增标注数据进行模型微调，提升准确率
  • 每季度评估模型整体表现，调整置信度阈值和优先级策略

8.3.4 审计追溯能力

文档智能处理系统的所有操作必须留痕，支持完整的审计追溯：

追溯要素说明
操作日志记录所有用户操作，包括上传、审查、复核、确认、驳回
版本记录记录文档的每个处理版本，支持版本对比
结果快照记录AI的每个判断结果和证据链，不可篡改
审批轨迹记录每个审批节点的操作人和操作时间

审计追溯能力是系统通过法务、审计、监管审查的必要条件。在金融、医疗等强监管行业，审计追溯能力本身就是合规要求的一部分。

8.3.5 本章小结

文档与合同智能处理系统的证据链必须包含原文位置、风险规则、历史案例和企业规范四个要素。低置信度字段自动进入人工复核队列，按字段重要性排序优先级。人工复核结果作为标注数据回流到模型训练流程，形成持续优化的闭环。系统的所有操作必须留痕，支持完整的审计追溯，这是通过法务、审计和监管审查的必要条件。
