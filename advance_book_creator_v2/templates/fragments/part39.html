第三十九章 智能问数——核心误区与数据权限

7.3 核心认知误区警示与数据权限体系

智能问数落地的最大风险不是技术问题，而是认知问题。如果企业在认知层面没有纠偏，技术投入越多，风险越大。本节从核心误区警示和数据权限两个维度，为产品经理和架构师提供风险防控框架。

7.3.1 核心误区警示

🔴 最高风险警告： 直接让大模型看数据库schema生成SQL并执行，风险极高。这不是一个"可以用"的方案，而是一个"绝不能用"的方案。

为什么这个方案风险极高？ 风险一：SQL注入与数据泄露

大模型不理解企业的数据权限体系。它可能生成包含敏感字段的查询，或者绕过行级权限约束，导致数据泄露。

-- 模型可能生成的危险SQL（用户只能看自己部门的数据）
SELECT * FROM user_salary  -- 包含了全公司的薪资数据！
WHERE department_id IN (1, 2, 3, 4, 5, ...)  -- 没有权限过滤
风险二：口径不一致导致决策失误

没有统一指标层的情况下，模型每次生成的SQL可能对同一指标使用不同的计算逻辑。

-- 第一次查询"活跃用户"：登录过就算活跃
SELECT COUNT(DISTINCT user_id) FROM user_login WHERE date = '2025-01-01'

-- 第二次查询"活跃用户"：登录且有操作才算活跃
SELECT COUNT(DISTINCT user_id) FROM user_login WHERE date = '2025-01-01' AND action_count > 0

-- 同一个问题，两次不同的答案，管理层该信哪个？
风险三：SQL错误隐蔽性高

大模型生成的SQL语法可能完全正确，但逻辑可能错误。这种错误比语法错误更危险，因为：

  • 查询能正常执行，不会报错
  • 返回的结果看起来合理，不易察觉
  • 基于错误数据做出的决策可能造成重大损失
-- 表面正确的SQL，实际逻辑错误
-- 用户问："上月各品类销售额"
-- 模型生成的SQL可能：
-- 1. JOIN关系错误（LEFT JOIN写成INNER JOIN）
-- 2. 聚合逻辑错误（SUM写成了AVG）
-- 3. 时间过滤错误（过滤了下单时间而非支付时间）
-- 4. 去重逻辑缺失（重复计算的订单）

💡 正确路径： 智能问数的正确架构是"语义层生成查询计划 → SQL校验器检查 → 再执行"。大模型不应该直接面对裸露的数据库schema，而应该通过指标语义层的中间层进行查询。

7.3.2 数据权限体系

数据权限是智能问数系统的核心安全基础设施。必须实现以下四个层面的权限控制：

层面一：行级权限（Row-Level Security）

行级权限控制用户能访问哪些数据行。

权限类型控制逻辑示例
部门维度用户只能查看本部门数据华东区经理只能看华东区数据
角色维度不同角色看到不同粒度的数据高管看全公司，中层看部门，基层看个人
客户维度销售只能查看自己负责的客户销售A只能看客户A的数据

行级权限的实现方式：

-- 在SQL生成后自动注入权限过滤条件
-- 原始查询：SELECT * FROM orders WHERE month = '2025-01'
-- 注入权限后：SELECT * FROM orders WHERE month = '2025-01' AND region_id = 'east_china'
层面二：列级权限（Column-Level Security）

列级权限控制用户能访问哪些数据列。

权限类型控制逻辑示例
敏感字段普通用户无法查看敏感列薪资、身份证号、银行卡号等
聚合可见普通用户只能查看聚合值可查看平均薪资，不可查看个人薪资
脱敏展示部分可见但需要脱敏手机号显示为 138**1234
层面三：敏感字段脱敏

对于必须展示的敏感数据，需要进行脱敏处理。

字段类型脱敏规则示例
手机号中间4位掩码138**1234
身份证号后8位掩码110101**1234
邮箱用户名部分掩码u*@example.com
银行卡号保留后4位* * 1234
姓名保留首尾张*明
层面四：SQL审计与用户操作日志

所有通过智能问数系统执行的查询都必须被审计和记录。

审计项记录内容用途
用户信息用户ID、角色、部门权限追溯
查询内容原始问题、生成SQL、修改SQL问题定位和口径追溯
执行结果返回行数、执行时间、数据量性能监控和异常检测
权限检查行级权限结果、列级权限结果、脱敏记录安全合规审计
时间戳查询时间、结果缓存命中情况时效性分析

审计日志的保留期限建议：

  • 普通查询日志：保留6个月
  • 敏感数据查询日志：保留2年
  • 权限变更记录：永久保留

7.3.3 口径管理体系

口径管理是确保智能问数数据一致性的核心机制。

指标口径版本管理

每个指标都应该有明确的版本管理：

指标: GMV
版本: v2.1
定义: 用户在平台上下单并支付的订单总金额
计算公式: SUM(order_amount) WHERE pay_status = 'PAID'
时间口径: 以支付时间为准，非下单时间
退款处理: 退款订单不计入GMV（已在支付状态过滤）
生效日期: 2025-01-01
历史版本:
  - v1.0 (2024-01-01 ~ 2024-06-30): 包含未支付订单
  - v2.0 (2024-07-01 ~ 2024-12-31): 排除未支付，但未排除退款
  - v2.1 (2025-01-01 ~ 至今): 排除未支付+排除退款
同义词库

建立业务同义词库，确保用户用不同表达查询同一指标时，得到一致的结果。

标准指标名称同义词/别名
GMV交易额、成交金额、支付金额、流水
活跃用户DAU、日活、日活跃用户、当日登录用户
转化率购买转化率、下单转化率、支付转化率
毛利率毛利百分比、利润率
复购率回头率、二次购买率
口径变更通知机制

当指标口径发生变更时，必须通知所有相关用户：

  • 在查询结果中提示口径变更
  • 在指标详情页展示口径变更历史
  • 对重要口径变更发送系统通知
  • 保留历史口径的查询能力（支持时间旅行查询）

7.3.4 权限与口径的结合

权限和口径不是独立工作的，而是需要紧密结合：

用户提问 → 语义层解析（匹配指标口径） → 权限层注入（行级+列级权限）
→ SQL校验器（安全检查） → 查询执行 → 结果脱敏 → 返回用户

在每个环节都需要同时考虑权限和口径：

  • 语义层解析：确保使用正确的指标口径版本
  • 权限层注入：确保查询结果在用户的权限范围内
  • SQL校验器：确保SQL没有绕过权限控制
  • 结果脱敏：确保敏感数据在展示前已脱敏

7.3.5 本章小结

智能问数的核心认知误区是"直接让大模型看数据库schema生成SQL"，这种方案风险极高，可能导致SQL注入、数据泄露、口径不一致和隐蔽的逻辑错误。正确的架构是通过指标语义层的中间层进行查询。数据权限体系包括行级权限、列级权限、敏感字段脱敏和SQL审计四个层面。口径管理体系包括指标口径版本管理和同义词库建设。权限和口径需要紧密结合工作，确保每次查询的口径一致性和数据安全性。
