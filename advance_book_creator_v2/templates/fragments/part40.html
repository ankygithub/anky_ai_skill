第四十章 智能问数——系统整体架构

7.4 工程架构设计

智能问数的系统架构是保障数据安全性、口径一致性和查询效率的核心基础设施。本节从架构视角完整拆解智能问数系统的组成和各组件的职责边界。

7.4.1 架构核心原则

🔴 核心原则：不要让大模型直接连生产库自由查询。 这是智能问数架构设计的铁律，不可妥协。

这条铁律背后有三个不可动摇的理由：

  1. 安全风险：大模型不理解数据权限体系，可能生成越权查询
  2. 口径混乱：大模型不理解指标口径，每次生成的SQL可能逻辑不一致
  3. 性能灾难：大模型可能生成低效SQL，拖垮生产数据库

7.4.3 核心组件详解

组件一：数据仓库/数据湖

数据仓库是智能问数的底层数据源，但绝对不是生产数据库。

特征说明
数据同步通过CDC或ETL从生产库同步到数据仓库，延迟控制在5分钟内
只读访问智能问数系统只能读取数据仓库，不能写入
独立集群数据查询使用独立的计算集群，不影响生产系统
数据分层ODS → DWD → DWS → ADS，查询优先在DWS/ADS层执行

⚠️ 架构铁律： 智能问数系统只能查询数据仓库的只读副本，绝不能直接连接生产数据库。这是防止大查询拖垮生产系统的最后一道防线。

组件二：指标平台

指标平台是企业统一指标管理的核心系统。

核心能力：

能力说明
指标定义通过YAML/可视化界面定义指标的计算逻辑
指标计算预计算或实时计算指标值
指标血缘追溯指标的数据来源和计算路径
指标版本管理指标口径的变更历史
指标审批指标定义的创建、修改需要审批流程

指标定义示例：

metric:
  name: gmv
  display_name: GMV（交易总额）
  description: 用户在平台上下单并支付的订单总金额
  calculation:
    type: sum
    field: order_amount
    filter:
      - field: pay_status
        operator: equals
        value: PAID
      - field: order_type
        operator: not_equals
        value: CANCELLED
  time_field: pay_time
  granularity: [day, week, month, quarter, year]
  dimensions: [region, category, channel, user_level]
  version: v2.1
  owner: data_team
组件三：语义层 语义层是智能问数系统的核心中枢，负责将自然语言映射为数据查询。

语义层的组成：

组件说明示例
指标字典所有指标的定义、计算逻辑、口径GMV、DAU、转化率等
维度字典所有维度的定义、枚举值、层级关系地区（国家→省→市）、时间（年→季→月→日）
同义词库指标和维度的业务别名GMV = 交易额 = 成交金额
业务词典业务术语解释和领域知识"高价值客户" = 月消费 > 1000元

语义层在查询中的作用：

用户提问："上月华东区GMV环比增长多少？"
       │
       ▼ 语义层解析
{
  "metrics": [{"name": "gmv", "period": "last_month"}],
  "dimensions": [{"name": "region", "value": "华东区"}],
  "operations": [{"type": "mom", "metric": "gmv"}],  // month-over-month
  "time_range": {"start": "2025-04-01", "end": "2025-04-30"}
}
组件四：权限层

权限层负责在查询执行前注入权限过滤条件。

权限层工作流程：

SQL生成器输出的SQL
       │
       ▼ 查询用户权限
{
  "row_permissions": ["region_id = 'east_china'"],
  "column_permissions": {"hide": ["salary", "id_card"], "mask": ["phone", "email"]},
  "role": "regional_manager"
}
       │
       ▼ 注入权限条件
SELECT region, SUM(gmv) FROM orders
WHERE month = '2025-04' AND region_id = 'east_china'  -- 自动注入
GROUP BY region
组件五：SQL生成器

SQL生成器负责将语义层的结构化查询转换为可执行的SQL。

SQL生成策略：

策略说明适用场景
模板生成基于预定义的SQL模板填充参数简单查询（单指标+维度过滤）
AST构建基于抽象语法树构建SQL复杂查询（多表JOIN+子查询）
LLM生成使用大模型生成SQL灵活查询（非标准分析需求）

💡 架构建议： SQL生成应该以模板生成和AST构建为主，LLM生成为辅。模板和AST确保口径一致性，LLM处理非标准查询的灵活性。

组件六：SQL校验器

SQL校验器是智能问数的安全守门人，负责在查询执行前进行多维度安全检查。

校验维度：

校验项检查内容处理方式
表权限查询的表是否在当前用户权限范围内无权限 → 拦截
字段权限查询的字段是否在当前用户权限范围内无权限 → 拦截或替换为脱敏版本
扫描量预估扫描的数据量是否超过限制超限 → 拦截，建议缩小时间范围
聚合逻辑聚合函数和GROUP BY是否匹配不匹配 → 修正或警告
时间范围查询的时间范围是否合理过大 → 警告，建议缩小范围
敏感字段是否包含敏感字段包含 → 自动脱敏或拦截
组件七：查询执行器

查询执行器负责在数据仓库的只读副本上执行查询。

执行策略：

策略说明
超时控制查询执行时间超过30秒自动终止
资源限制单个查询的CPU和内存使用上限
并发控制限制同时执行的查询数量，防止资源竞争
结果缓存相同查询的命中缓存，减少重复执行
限流熔断查询失败率超过阈值时触发熔断
组件八：图表生成器

图表生成器负责根据数据类型自动推荐合适的可视化图表。

图表推荐规则：

数据类型推荐图表示例
单值指标数字卡片"GMV: 1,234万元"
时间序列折线图/面积图月度GMV趋势
分类对比柱状图/条形图各品类销售额对比
占比分析饼图/环形图各渠道销售占比
分布分析散点图/直方图客户消费分布
地域分析地图/热力图各省销售分布
多维对比堆叠柱状图/雷达图多指标对比
组件九：解释生成器

解释生成器负责将查询结果转化为自然语言解释。

解释生成内容：

  • 核心结论：用一句话总结查询结果
  • 关键发现：数据中的异常和趋势
  • 追问建议：基于结果的后续分析建议
用户查询结果：华东区上月GMV为1,234万元，环比增长5.2%

解释生成：
"上月华东区GMV为1,234万元，环比增长5.2%，同比增长12.8%。
其中浙江省贡献最大（45%），上海市增速最快（+8.3%）。
建议关注江苏省环比下降2.1%的情况。"

7.4.4 架构部署模式

根据不同企业的规模和需求，智能问数系统支持三种架构部署模式：

模式一：轻量级模式（中小企业） 
用户 → API Gateway → 智能问数服务 → 数据仓库只读副本
  • 语义层、权限层、SQL生成器部署在同一服务中
  • 使用云端数据仓库（如MaxCompute、ClickHouse）
  • 适合数据量 < 1TB的团队
模式二：标准模式（中大型企业） 
用户 → API Gateway → 语义层服务 → 权限层服务 → SQL生成器 → SQL校验器
                                              → 查询执行器 → 数据仓库
  • 各组件独立部署，支持水平扩展
  • 指标平台和语义层分离管理
  • 适合数据量 1TB-100TB的企业
模式三：企业级模式（超大型企业） 
用户 → 负载均衡 → 智能问数网关 → 语义层集群 → 权限层集群
                              → SQL生成集群 → SQL校验集群
                              → 查询执行集群 → 数据仓库集群
  • 全组件集群化部署，支持高可用和容灾
  • 多租户隔离，不同业务线独立部署
  • 适合数据量 > 100TB的集团型企业

7.4.5 本章小结

智能问数的工程架构包含数据仓库、指标平台、语义层、权限层、SQL生成器、SQL校验器、查询执行器、图表生成器和解释生成器九个核心组件。架构核心原则是"不要让大模型直接连生产库自由查询"。SQL生成应以模板和AST为主、LLM为辅，确保口径一致性。架构部署模式分为轻量级、标准级和企业级三种。理解这些架构组件和设计要求，是构建安全、可靠的智能问数系统的基础。
