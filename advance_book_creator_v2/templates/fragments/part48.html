第四十八章 文档与合同智能处理——多模型流水线架构

8.4 多模型流水线设计与实现

多模型流水线是文档智能处理系统的核心架构模式。其核心理念与第8.1节强调的第一原则一致：不要把所有事情交给一个LLM。本节详细阐述多模型流水线的架构设计、各阶段模型选型和编排实现。

8.4.1 为什么不能把一切交给一个LLM

在文档处理领域，"一个大模型解决所有问题"的方案在实践中暴露了多个致命缺陷：

缺陷说明影响
信息丢失扫描件中的印章、签名、表格边框等视觉信息无法通过纯文本传递关键信息遗漏
上下文窗口限制长文档（50页以上）超出模型上下文窗口，被迫截断后半部分内容完全忽略
精度不足LLM擅长语义推理，但在精确的OCR识别和字段定位上不如专用模型金额、日期等关键字段识别错误
成本高昂大模型处理长文档的Token消耗是专用模型的10-100倍单次处理成本不可接受
无法审计纯LLM的端到端输出难以追溯具体判断依据不满足法务合规要求
难以优化端到端方案出问题后难以定位是哪个环节出错优化方向不明确

💡 架构铁律： 每个模型只做它最擅长的事。OCR模型做文字识别，版面模型做结构理解，信息抽取模型做字段定位，大模型做条款解释，规则引擎做合规校验。分工明确，各施所长。

8.4.2 五阶段流水线架构

标准的文档智能处理流水线包含五个阶段：

阶段一：OCR模型（文字识别）

OCR模型的职责是将扫描文档或图片中的文字识别为可计算文本。

选型维度推荐方案
通用OCRPaddleOCR、Tesseract 5.x
中文优化PaddleOCR（中文识别准确率领先）
手写体识别百度OCR API、腾讯云OCR
商业级高精度合合信息、ABBYY FineReader

关键指标要求：

  • 印刷体中文识别准确率 > 98%
  • 手写体中文识别准确率 > 85%
  • 低质量图像（模糊、倾斜、光照不均）增强后识别准确率 > 90%
阶段二：版面分析模型（结构理解）

版面分析模型的职责是识别文档中的结构元素，建立文档的逻辑结构。

结构元素说明
标题一级/二级/三级标题识别，用于建立文档大纲
段落普通文本段落，用于后续语义分析
表格表格区域检测和结构解析
印章公章位置检测和完整性验证
签名手写签名区域检测
页眉/页脚排除重复信息，避免干扰字段抽取
图片文档中的插图区域标记

推荐的版面分析方案：

  • 开源方案：LayoutLMv3（微软）、DocStruct
  • 商业方案：合合信息文档结构化、百度文档结构化API

版面分析的输出是一个结构化的文档对象模型（Document Object Model, DOM），包含每个结构元素的类型、位置和文本内容。

阶段三：信息抽取模型（字段提取）

信息抽取模型的职责从结构化文档中提取关键字段。

字段类型抽取方法说明
正则字段正则表达式日期、金额、身份证号、统一社会信用代码等
规则字段模板匹配标准合同中的固定位置字段
语义字段NER模型当事人名称、地址、争议解决地等
关系字段关系抽取模型甲方/乙方的对应关系、金额与币种的关联

推荐的抽取方案：

  • 正则+规则：适用于标准化程度高的字段（日期、金额、编号）
  • BERT/RoBERTa NER：适用于语义型字段（当事人、地址）
  • Prompt-based LLM：适用于复杂推理型字段（付款条件、违约责任摘要）

⚠️ 关键提醒： 信息抽取阶段应尽量使用轻量级模型，避免不必要的大模型调用。只有在正则和规则无法覆盖的场景才使用LLM，这是控制成本的关键。

阶段四：大模型（条款解释与风险分析）

大模型的职责是对抽取出的条款进行语义理解和风险分析。

大模型在流水线中的典型应用场景：

场景说明提示词示例
条款分类判断某段落属于哪种合同条款类型"请判断以下条款的类型：{条款文本}"
风险识别识别条款中的潜在风险点"请分析以下条款是否存在法律风险：{条款文本}"
风险解释解释为什么某条款存在风险"请解释以下条款的风险原因，并引用相关法规：{条款文本}"
修改建议提供条款修改建议"请提供以下条款的修改建议，使其更符合甲方利益：{条款文本}"
多版本差异解释解释两个版本条款的实质差异"请分析以下两个条款版本的核心差异：{版本A}{版本B}"

大模型调用的优化策略：

  • 只输入必要内容：不将整个合同发送给大模型，只输入需要分析的特定条款
  • 结构化提示词：使用模板化的提示词，确保输出格式统一
  • 结果缓存：相同条款的分析结果缓存复用，避免重复调用
阶段五：规则引擎（硬性合规检查）

规则引擎的职责是执行不可妥协的硬性合规检查，这些检查不依赖AI判断，而是基于明确的法规和企业规范。

规则类型示例
法规强制要求劳动合同必须包含工作时间、休息休假条款
行业监管要求金融合同必须包含风险提示条款
企业内控标准采购合同金额超过100万必须经过法务审查
禁用词规则营销文案中不得使用"最""第一""绝对"等词汇
数值校验规则违约金比例不得超过合同总金额的30%

规则引擎的实现方式：

  • DSL规则语言：使用Drools等规则引擎，将合规规则表达为可执行的DSL
  • 配置化规则：通过配置文件管理规则，支持热更新
  • 版本管理：规则版本与法规版本关联，支持历史规则回溯

8.4.3 流水线编排实现

流水线的编排需要处理以下关键问题：

并行与串行

不是所有阶段都必须串行执行。某些阶段可以并行处理以提高效率：

class PipelineOrchestrator:
    """流水线编排器"""
    
    async def process_document(self, document: Document) -> PipelineResult:
        # 阶段1+2：OCR和版面分析可以并行启动
        ocr_task = asyncio.create_task(self.ocr_engine.recognize(document))
        layout_task = asyncio.create_task(self.layout_analyzer.analyze(document))
        
        ocr_result, layout_result = await asyncio.gather(ocr_task, layout_task)
        
        # 合并OCR和版面结果
        structured_doc = self.merge_results(ocr_result, layout_result)
        
        # 阶段3：信息抽取（依赖阶段1+2的结果）
        extracted_fields = await self.field_extractor.extract(structured_doc)
        
        # 阶段4+5：大模型分析和规则引擎可以并行
        llm_task = asyncio.create_task(
            self.llm_analyzer.analyze(structured_doc, extracted_fields)
        )
        rule_task = asyncio.create_task(
            self.rule_engine.check(extracted_fields)
        )
        
        llm_result, rule_result = await asyncio.gather(llm_task, rule_task)
        
        # 汇总结果
        return self.assemble_result(
            structured_doc, extracted_fields, llm_result, rule_result
        )
错误处理与降级

流水线中的每个阶段都可能失败，必须有完善的错误处理和降级机制：

阶段失败降级策略
OCR失败尝试备用OCR引擎；如果仍然失败，标记为"无法识别"并进入人工处理
版面分析失败降级为纯文本处理模式，跳过版面结构信息
信息抽取失败使用大模型进行兜底抽取（成本更高但覆盖更广）
大模型超时返回已完成的抽取结果，标记风险分析"待补充"
规则引擎异常跳过规则检查，在结果中标注"合规检查未执行"
结果汇总

流水线的最终输出是一个结构化的处理结果，包含每个阶段的中间结果和最终结论。这种设计既支持完整的结果展示，也支持针对特定阶段的调试和优化。

生产环境的流水线需要完善的监控体系：

监控指标说明告警阈值

8.4.5 本章小结

多模型流水线是文档智能处理的核心架构，包含OCR模型、版面分析模型、信息抽取模型、大模型和规则引擎五个阶段。每个阶段只做它最擅长的事，避免将一切交给单一LLM。流水线编排需要考虑并行与串行、错误处理与降级、结果汇总等关键问题。生产环境需要完善的监控体系，确保流水线的稳定性和持续优化。
