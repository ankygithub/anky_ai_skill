第二十四章 企业知识库——查询改写与向量数据库

从"用户说什么"到"系统怎么理解"——提升检索质量的两个关键环节

5.7.1 查询改写的必要性

用户提问的方式千变万化，但知识库中的知识有其特定的表述方式。查询改写（Query Rewriting）的核心目标是将用户的原始问题转化为更适合检索的形式，从而提升召回率和准确率。

用户问题 vs 改写后问题：
用户原始问题改写后问题改写策略
"年假怎么算？""年休假天数计算规则 累计工作年限对应年休假天数"意图澄清+关键词提取
"报销要什么？""费用报销 所需材料 流程 发票 审批单"意图澄清+关键词扩展
"新人来要干嘛？""新员工入职流程 培训安排 入职手续"意图澄清+同义词替换
"年假有几天？病假有几天？婚假呢？"["年假有几天？", "病假有几天？", "婚假有几天？"]问题分解
"公司的加班制度是什么样的？""加班管理制度 加班时长限制 加班费计算标准 加班审批流程"HyDE假设文档

5.7.2 查询改写三大策略

策略一：意图澄清

意图澄清通过识别用户问题中的模糊表达，将其改写为更精确、更具体的查询。 实现方式： 
用户问题 ──→ LLM意图分析 ──→ 提取核心实体和意图 ──→ 生成精确查询
                ↓
         判断问题类型：
         - 事实型（是什么/有多少人）
         - 流程型（怎么做/流程是什么）
         - 政策型（规定/制度/要求）
         - 对比型（A和B有什么区别）
改写示例：
用户问题问题类型改写结果
"年假怎么算？"政策型"年休假天数计算规则 按累计工作年限确定年休假天数"
"怎么申请报销？"流程型"费用报销申请流程 步骤 审批 所需材料"
"Qwen和GPT哪个好？"对比型"通义千问 Qwen 与 GPT 对比 性能 成本 中文能力"

策略二：问题分解

问题分解适用于用户在一个问题中包含多个子问题的场景。将复合问题拆分为多个简单问题，分别检索后再合并答案。 分解规则：
复合问题类型示例分解结果
并列问题"年假和病假分别有几天？"①"年假有几天？" ②"病假有几天？"
条件问题"工作满5年的人年假有几天，能结转吗？"①"工作满5年年休假天数" ②"年休假能否结转下年"
多步骤问题"请假流程是什么，需要提前几天，领导不批怎么办？"①"请假流程" ②"请假提前申请天数" ③"请假审批被拒处理方式"
实现伪代码： 
def decompose_query(question: str) -> list[str]:
    """将复合问题分解为多个简单问题"""
    prompt = f"""
    请将以下用户问题分解为多个独立的简单子问题。
    每个子问题应该能独立检索到答案。
    
    用户问题：{question}
    
    请返回JSON数组格式的子问题列表：
    ["子问题1", "子问题2", ...]
    """
    result = llm.generate(prompt)
    return json.loads(result)

# 使用示例
sub_questions = decompose_query("年假和病假分别有几天？")
# 输出：["年假有几天？", "病假有几天？"]

策略三：HyDE假设文档

HyDE（Hypothetical Document Embeddings）是一种创新的检索策略：先生成一个"假设性答案文档"，然后用这个假设文档去检索，而非直接用原始问题去检索。 核心思想：大语言模型生成的假设文档（即使不准确）在向量空间中与真实答案文档的相似度，往往高于原始问题与真实答案文档的相似度。 流程： 
用户问题 ──→ LLM生成假设文档 ──→ 假设文档向量化 ──→ 检索真实文档
 "年假有几天？"   "员工连续工作满12个月，    "年假有几天？的向量     找到真实的年假制度文档
                   享受带薪年休假……"
适用场景：
场景传统检索HyDE检索
用户问题简短"年假" → 召回各种含"年假"的文档LLM生成完整问题描述 → 更精准匹配
用户问题模糊"请假相关" → 召回所有含"请假"的文档LLM生成具体的请假制度内容 → 匹配最相关文档
专业术语不熟悉"TSR是什么？" → 可能匹配不到LLM生成技术解释 → 匹配含TSR定义的技术文档
⚠️ HyDE使用注意

HyDE虽然能提升检索效果，但有两个需要注意的问题：

  • 延迟增加：需要额外调用一次LLM生成假设文档，增加约200-500ms延迟
  • 幻觉风险：假设文档中的错误信息可能影响检索方向，需要控制生成温度和长度

建议：仅在传统检索召回率不足时启用HyDE，作为"备选策略"而非"默认策略"。

5.7.3 向量数据库选型

向量数据库是RAG系统的核心基础设施，负责存储和检索高维向量数据。2026年市场上主流的向量数据库包括：

选型对比

数据库类型部署方式优势适用场景
Milvus专用向量数据库开源/云托管功能最全面、社区活跃、HNSW+IVF索引、支持PB级大规模知识库、高性能要求
Elasticsearch搜索引擎（8.0+支持向量）开源/商业同时支持BM25和向量检索、生态成熟已有ES基础设施的企业
OceanBase分布式关系数据库（4.x+支持向量）开源/商业事务支持、企业级、与现有OB生态集成已使用OceanBase的企业
PolarDB+pgvectorPostgreSQL扩展云托管与关系型数据库集成、SQL+向量混合查询已有PostgreSQL生态的企业
Qdrant专用向量数据库开源/云托管轻量级、Rust实现、高性能、API简洁中小规模、快速部署

选型决策矩阵

是否需要与现有数据库集成？
    ├── 是 → 已有Elasticsearch？→ 使用ES 8.0+向量检索
    │       ├── 已有OceanBase？→ 使用OB 4.x向量检索
    │       └── 已有PostgreSQL？→ 使用pgvector
    │
    └── 否 → 数据规模？
            ├── <100万向量 → Qdrant（轻量快速）
            ├── 100万-1亿向量 → Milvus（功能全面）
            └── >1亿向量 → Milvus分布式部署

5.7.4 查询改写与向量检索的协同

查询改写和向量检索不是独立的两个环节，而是协同工作的整体：

用户问题
    ↓
┌─────────────────────┐
│  查询改写模块         │
│  ① 意图澄清          │
│  ② 问题分解          │
│  ③ HyDE（可选）      │
└──────┬──────────────┘
       ↓ 改写后的查询
┌─────────────────────┐
│  多路召回模块         │
│  向量检索 + BM25     │
└──────┬──────────────┘
       ↓ 候选文档
┌─────────────────────┐
│  重排模块            │
│  bge-reranker        │
└──────┬──────────────┘
       ↓ Top-5文档
┌─────────────────────┐
│  答案生成            │
└─────────────────────┘

5.7.5 本章小结

查询改写是RAG管道的"前置放大器"，通过意图澄清、问题分解和HyDE三种策略，将用户的原始问题转化为更适合检索的形式。向量数据库选型需要根据企业现有技术栈和数据规模做出决策——Milvus适合大规模专用场景，Elasticsearch适合已有ES基础设施的企业，Qdrant适合中小规模快速部署。查询改写和向量检索的协同设计，是提升RAG系统整体检索质量的关键。下一章将深入讲解文档处理与权限控制。
