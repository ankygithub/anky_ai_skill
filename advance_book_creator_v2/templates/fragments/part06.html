第六章 通用技术底座

从"零散搭建"到"构建可复用的AI基础设施"

6.1 八项基础设施概述

无论AI系统的具体场景是什么——智能客服、知识助手、代码工具还是数据分析——都需要依赖一套共通的基础设施。我们将这些基础设施归纳为八项核心能力：

序号基础设施核心功能类比
1模型网关统一模型调用、路由、降级"AI的负载均衡器"
2RAG知识引擎文档解析、向量化、检索增强"AI的知识中枢"
3智能体编排任务规划、工具调度、流程管理"AI的工作流引擎"
4沙箱执行代码隔离、工具权限、安全边界"AI的安全笼子"
5权限身份认证、授权、多租户、配额"AI的门卫和会计"
6可观测性日志、指标、追踪、质量评估"AI的仪表盘和黑匣子"
7评测系统测试集、自动评估、基准对比"AI的考试中心"
8成本控制Token计量、费用分摊、优化建议"AI的财务系统"

这八项基础设施是AI系统的技术底座。没有它们，AI系统就像没有地基的房子——可以搭起来，但经不起生产环境的考验。

6.2 模型网关：AI的流量调度中枢

6.2.1 为什么需要模型网关？

在没有模型网关的情况下，每个AI应用直接调用模型API，导致：

  • 厂商锁定：业务代码与特定模型API深度耦合
  • 无法降级：主模型故障时没有自动切换机制
  • 成本失控：没有统一的Token计量和成本控制
  • 版本混乱：不同应用使用不同的模型版本，无法统一管理
模型网关 在AI应用和模型服务之间增加了一个中间层，统一封装所有模型调用，提供路由、降级、计量、缓存等能力。

6.2.2 核心能力

能力说明业务价值
统一接口将不同厂商的API统一为标准接口降低厂商切换成本
智能路由根据任务类型、成本、延迟自动选择模型性价比最大化
故障降级主模型不可用时自动切换到备用模型保障系统可用性
Token计量精确记录每次调用的Token消耗成本核算和优化
请求缓存相似请求直接返回缓存结果降低重复调用成本
速率控制限制每个应用/用户的调用频率防止滥用和资源耗尽
Prompt管理Prompt模板的存储、版本化和A/B测试保证一致性、支持迭代优化

6.3 RAG知识引擎：AI的知识中枢

6.3.1 RAG的完整管线

RAG知识引擎 不仅仅是"向量数据库"，而是一个完整的知识处理管线：
步骤一：文档采集

从各种来源采集原始文档：文件系统、数据库、网页、API、IM聊天记录等。需要处理不同格式（PDF、Word、Excel、PPT、HTML、Markdown）。

步骤二：文档解析

将各种格式的文档解析为纯文本或结构化数据。关键挑战：保留文档结构（标题、段落、表格、列表）、处理复杂排版（多栏PDF、扫描件OCR）。

步骤三：文本分块

将长文本切分为适合向量化的块（Chunk）。分块大小的权衡：太大 → 检索精度低；太小 → 上下文不完整。推荐：500-1500 tokens/块，20%重叠。

步骤四：向量嵌入

使用嵌入模型（Embedding Model）将文本块转换为向量。嵌入模型的选择直接影响检索质量。推荐：text-embedding-3-large（OpenAI）、bge-large-zh（智谱）。

步骤五：向量入库

将向量及其元数据存储到向量数据库中。元数据包括：原文档ID、分块位置、更新时间、权限标签等，用于检索时的过滤。

步骤六：检索增强

用户提问时，将问题向量化后在数据库中检索最相关的Top-K个块，将其作为上下文注入模型Prompt，生成最终回答。

6.3.2 提升RAG质量的关键策略

策略说明效果提升
混合检索向量检索 + 关键词检索（BM25）组合+10-15% 召回率
查询重写将用户问题改写为更适合检索的形式+8-12% 准确率
多级检索先用粗筛、再用精排+5-10% 精准度

6.4 智能体编排：AI的工作流引擎

6.4.1 为什么需要编排层？

Agent不是"调一个模型"就完了。一个完整的Agent任务包含：

理解意图 → 制定计划 → 选择工具 → 执行工具 → 解析结果 → 决定下一步 → ... → 生成最终回答

这个过程可能包含 5-50 个步骤，每个步骤都可能失败，需要重试、回退、降级。智能体编排层 就是管理这个复杂流程的基础设施。

6.4.2 编排层核心能力

能力说明
任务拆解将复杂任务拆分为可执行的子任务
工具注册与发现管理所有可用工具的描述、参数和权限
流程控制串行、并行、条件分支、循环、超时控制
状态管理维护Agent执行过程中的中间状态
错误处理重试策略、降级策略、人工介入机制
记忆管理短期记忆（会话上下文）和长期记忆（跨会话知识）
审计追踪记录Agent的每一步操作，支持事后追溯

6.4.3 编排架构模式

模式一：集中式编排（Orchestrator Pattern） 
             ┌─────────────┐
             │  中央编排器  │
             └──┬──┬──┬──┬─┘
                │  │  │  │
          ┌─────┘  │  │  └─────┐
          ▼        ▼  ▼        ▼
      ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
      │Agent A│ │Agent B│ │Agent C│ │工具库│
      └──────┘ └──────┘ └──────┘ └──────┘

一个中央编排器负责任务拆解和调度，各Agent是"执行者"。适合需要强控制的场景。

模式二：去中心化协作（Multi-Agent Pattern） 
    ┌────────┐    ┌────────┐
    │Agent A │◄──►│Agent B │
    │(规划者) │    │(执行者) │
    └───┬────┘    └────┬───┘
        │              │
        ▼              ▼
    ┌────────┐    ┌────────┐
    │Agent C │◄──►│Agent D │
    │(审核者) │    │(工具库) │
    └────────┘    └────────┘

多个Agent自主协作，通过对话和消息传递完成任务。适合复杂、需要专业分工的场景。

6.5 沙箱执行：AI的安全笼子

6.5.1 沙箱的必要性

Agent具备调用工具和执行代码的能力。如果没有沙箱隔离，Agent可能：

  • 执行 rm -rf / 删除系统文件
  • 读取数据库中的敏感信息（密码、个人信息）
  • 调用支付API发起未授权交易
  • 陷入无限循环耗尽计算资源
沙箱执行层 为Agent的操作提供隔离环境，确保任何错误操作都不会影响生产系统。

6.5.2 沙箱能力矩阵

能力说明技术方案
进程隔离每个Agent运行在独立进程/容器中Docker、gVisor、Firecracker
网络隔离限制Agent可访问的网络范围网络策略、防火墙规则
文件系统隔离Agent只能访问授权的文件路径挂载只读文件系统、临时目录
资源限制CPU、内存、磁盘、时间的上限cgroups、K8s ResourceQuota
权限最小化只授予Agent必要的操作权限Linux capabilities、RBAC
超时控制长时间运行的Agent被强制终止Watchdog、超时中断
操作审计记录Agent的所有操作行为系统调用审计、日志记录

6.6 权限身份：AI的门卫和会计

6.6.1 双维度权限模型

AI系统的权限管理比传统系统复杂，因为它需要管理两个维度的权限：

维度一：用户权限（User Permissions）
  • 用户能访问哪些功能？
  • 用户能查看哪些数据？
  • 用户的Token用量配额是多少？
维度二：Agent权限（Agent Permissions）
  • Agent能调用哪些工具？
  • Agent能访问哪些数据源？
  • Agent能执行哪些操作（只读/写入/删除）？
权限设计原则

用户权限和Agent权限必须独立管理。用户有读取财务数据的权限，不代表用户的Agent可以有删除财务数据的权限。Agent的权限应该始终小于等于用户的权限，并且默认遵循最小权限原则。

6.6.2 多租户隔离

在多租户AI系统中，不同租户之间需要严格隔离：

隔离维度说明实现方式
数据隔离租户A的知识库不能泄露给租户B租户标签 + 查询过滤
模型隔离租户A的Prompt不影响租户BPrompt按租户隔离
配额隔离租户A的用量不影响租户B的配额独立计量和限流
计算隔离租户A的Agent不消耗租户B的资源容器/进程级别隔离

6.8 评测系统：AI的考试中心

6.8.1 为什么需要评测系统？

AI系统的概率性特征意味着你不能通过"跑几个测试用例"来验证质量。你需要一个系统化的评测体系：

  • 有一套代表性的测试集（Golden Dataset）
  • 有自动化的评估方法（LLM-as-a-Judge、RAGAS）
  • 有持续运行的评估流水线（CI/CD for AI）
  • 有可对比的基准分数（Baseline）

6.8.2 评测流程

步骤一：构建测试集

从真实用户问题中采样，构建代表性的测试集。覆盖：常见问题、边界场景、对抗样本、行业特定问题。建议：每个场景至少 100-500 个测试用例。

步骤二：定义评估标准

为每个测试用例定义标准答案或评分标准。对于主观性强的问题（如创意写作），使用多维度评分（准确性、完整性、可读性、安全性）。

步骤三：自动化评估

使用 RAGAS、LLM-as-a-Judge 等工具自动化评估。每次模型更新、Prompt变更、知识库更新后自动运行评估流水线。

步骤四：对比分析

将评估结果与基线对比，判断变更是"改善"还是"退化"。只有评估达标才能发布到生产环境。

6.8.3 评测指标

指标适用范围计算方法
忠实度（Faithfulness）RAG回答是否基于检索到的上下文
答案相关性问答回答与问题的相关程度
上下文相关性RAG检索到的上下文与问题的相关程度
上下文召回率RAG检索到的上下文覆盖了多少关键信息
安全性评分所有回答是否包含有害、违法、歧视性内容
一致性评分所有相同问题多次回答的一致性

6.9 成本控制：AI的财务系统

6.9.1 AI成本的构成

AI系统的成本结构与传统系统有很大不同：
成本类别占比说明
模型API费用40-60%按Token计费，是最大的可变成本
算力成本15-25%自部署模型的GPU/CPU成本
向量数据库5-15%存储和检索向量的成本
数据存储5-10%文档、日志、缓存的存储成本
网络带宽5-10%模型API调用、数据传输的网络成本
人力成本10-20%AI工程师、Prompt工程师、数据标注

6.9.2 成本优化策略

策略节省比例实施难度说明
模型路由30-50%中简单任务用小模型，复杂任务用大模型
请求缓存20-40%低相似问题直接返回缓存结果
Prompt优化10-20%低减少Prompt中的冗余Token
上下文裁剪10-30%中只保留相关的上下文片段
批量处理15-25%中合并多个小请求为批量请求
量化部署40-60%高自部署模型时使用INT4/INT8量化

6.9.3 成本可视化

成本管理建议

建立实时成本仪表盘，按以下维度拆解成本：

  • 按应用/功能：每个AI功能花费多少
  • 按用户/租户：每个用户/部门的花费
  • 按模型：每个模型的花费占比
  • 按时间：成本趋势和异常检测

没有成本可视化的AI系统，就像没有电表的家庭——你不知道钱花在了哪里，更不知道如何优化。

6.11 本章小结

本章详解了AI系统的八项通用技术底座：

基础设施一句话说明类比
模型网关统一模型调用、智能路由、故障降级AI的负载均衡器
RAG知识引擎文档解析→向量化→检索→增强生成AI的知识中枢
智能体编排任务规划、工具调度、流程管理AI的工作流引擎
沙箱执行代码隔离、工具权限、安全边界AI的安全笼子

这八项基础设施共同构成了AI系统的技术底座。没有它们，AI系统无法从Demo走向生产。有了它们，AI系统才能实现可扩展、可维护、安全可控、成本最优的生产级架构。
