第三章 AI系统分层架构

从"拼凑组件"到"系统化设计AI架构"

3.1 为什么需要分层架构？

在AI系统建设的初期，很多团队采用的是"拼凑式"做法：调一个API、接一个数据库、写一堆胶水代码，系统就"能跑了"。但当系统从Demo走向生产、从单一场景扩展到多场景时，这种拼凑式架构的问题就会全面暴露：

  • 耦合严重：模型切换需要改动业务代码
  • 不可观测：AI输出质量下降时无法定位原因
  • 安全缺失：模型可能执行危险操作，缺乏沙箱隔离
  • 成本失控：没有Token计量和成本控制
  • 难以扩展：新增一个Agent需要修改多处代码
分层架构 的核心思想是将AI系统的复杂性按照职责边界拆分为多个层次，每层有清晰的输入输出协议和职责范围。这样做的好处是：每层可以独立演进、独立替换、独立运维。

3.2 九层AI系统架构模型

基于对2026年主流AI系统实践的深度调研，我们提出以下九层架构模型：

┌──────────────────────────────────────────────────────────────┐
│  Layer 1: 用户入口层 (User Interface)                         │
│  网页 / 移动端 / API / 语音 / IM Bot / 嵌入式                  │
├──────────────────────────────────────────────────────────────┤
│  Layer 2: 身份权限层 (Identity & Access)                      │
│  认证 / 授权 / 多租户隔离 / 配额管理                           │
├──────────────────────────────────────────────────────────────┤
│  Layer 3: AI应用层 (AI Application)                           │
│  对话系统 / 内容生成 / 智能客服 / 代码助手 / 分析报表            │
├──────────────────────────────────────────────────────────────┤
│  Layer 4: 智能体编排层 (Agent Orchestration)                  │
│  任务规划 / 工具路由 / 多Agent协作 / 状态管理 / 记忆管理        │
├──────────────────────────────────────────────────────────────┤
│  Layer 5: 知识数据层 (Knowledge & Data)                       │
│  向量检索 / 知识图谱 / 文档解析 / 数据清洗 / 缓存               │
├──────────────────────────────────────────────────────────────┤
│  Layer 6: 工具业务层 (Tools & Business)                       │
│  业务API / 数据库操作 / 搜索引擎 / 第三方服务 / 文件处理        │
├──────────────────────────────────────────────────────────────┤
│  Layer 7: 模型服务层 (Model Serving)                          │
│  模型路由 / Prompt管理 / 模型网关 / 多模型适配 / 推理加速       │
├──────────────────────────────────────────────────────────────┤
│  Layer 8: 沙箱执行层 (Sandbox Execution)                      │
│  代码执行沙箱 / 工具调用隔离 / 安全策略 / 资源限制              │
├──────────────────────────────────────────────────────────────┤
│  Layer 9: 观测运营层 (Observability & Operations)             │
│  日志 / 指标 / 追踪 / 成本核算 / 质量评估 / 告警                │
└──────────────────────────────────────────────────────────────┘

这是一个从用户到基础设施的完整分层。每层向下依赖，向上提供服务。并非每个系统都需要全部九层，小型系统可以将多层合并，但理解完整的分层模型有助于做出正确的架构决策。

3.3 逐层职责详解

3.3.1 Layer 1: 用户入口层

核心职责：接收用户输入，呈现AI输出，管理交互体验。
入口类型适用场景交互特点
Web应用复杂业务系统、管理后台支持富文本、图表、多步骤流程
移动端AppC端用户、移动办公语音输入、拍照、推送通知
API接口第三方集成、系统对接无UI、纯数据交互、高并发
IM Bot内部协作、客服场景对话式交互、轻量级
语音入口智能音箱、车载场景全语音交互、低延迟要求高
关键设计要点：
  • 流式输出（Streaming）：LLM的生成是逐Token进行的，入口层必须支持流式展示，让用户"边生成边看"
  • 多模态输入：支持文本、图片、文件、语音等多种输入方式
  • 会话管理：维护用户的对话历史，支持多轮对话和上下文切换

3.3.2 Layer 2: 身份权限层

核心职责：管理用户身份、权限控制、多租户隔离和用量配额。
安全警示

AI系统的权限管理比传统系统更复杂：不仅要控制"谁能访问什么数据"，还要控制"AI能替用户做什么操作"。必须实现双维度权限：

  • 用户权限：用户能访问哪些资源和功能
  • Agent权限：AI智能体能调用哪些工具和API
核心组件：
  • 认证（Authentication）：OAuth 2.0、JWT、SSO单点登录
  • 授权（Authorization）：RBAC角色权限、ABAC属性权限
  • 多租户隔离：数据隔离、模型调用隔离、知识库隔离
  • 配额管理：Token用量限制、API调用频率限制、并发数控制

3.3.3 Layer 3: AI应用层

核心职责：面向用户的AI业务功能实现，是用户直接感知的"AI能力"。 典型应用类型：
应用类型核心功能技术要点
智能对话多轮问答、意图识别、上下文管理RAG、Prompt工程、会话状态机
内容生成文案、报告、邮件、PPT自动生成模板管理、格式约束、人工审核
智能客服自动问答、工单分派、情感分析知识库构建、兜底策略、人工转接
代码助手代码补全、Bug修复、Code Review代码解析、AST分析、安全扫描
数据分析SQL生成、图表生成、洞察总结Schema理解、数据可视化、统计校验

3.3.4 Layer 4: 智能体编排层

核心职责：Agent的任务规划、工具路由、多Agent协作和状态管理。这是AI系统区别于传统系统的核心差异层。 编排模式：
模式说明适用场景复杂度
单次调用用户输入→模型→输出简单问答、翻译低
ReAct推理→行动→观察循环需要工具调用的任务中
Plan-and-Execute先规划再执行多步骤复杂任务中高
多Agent协作多个专业Agent分工合作超复杂任务、需要专业分工高
反思迭代生成→评估→修正循环需要高质量输出的场景高
关键设计： 
用户请求 → 意图理解 → 任务拆解 → Agent调度 → 工具调用 → 结果聚合 → 质量检查 → 最终输出
  • 状态管理：Agent执行过程中需要维护中间状态，支持断点续传和回滚
  • 记忆管理：短期记忆（会话内上下文）+ 长期记忆（跨会话知识）
  • 超时和重试：Agent可能陷入死循环或长时间运行，需要设置超时和最大步数

3.3.5 Layer 5: 知识数据层

核心职责：管理AI系统需要的所有知识数据，包括向量化存储、知识图谱、文档解析和数据缓存。 核心组件：
组件功能代表技术
向量数据库存储和检索文本向量Milvus、Qdrant、Weaviate、Pinecone
知识图谱实体关系存储和推理Neo4j、JanusGraph
文档解析PDF/Word/Excel解析和分块Unstructured、LlamaIndex、LangChain
数据缓存热点数据缓存，降低模型调用Redis、Memcached
元数据管理文档版本、嵌入模型版本、分块策略自定义或DB
RAG数据流： 
原始文档 → 文档解析 → 文本分块 → 向量嵌入 → 向量入库
                                        ↓
用户提问 → 向量嵌入 → 相似度检索(Top-K) → 上下文组装 → LLM生成

3.3.6 Layer 6: 工具业务层

核心职责：为Agent提供可调用的外部工具和业务API。 工具分类：
类别示例安全等级
只读工具数据库查询、搜索引擎、文件读取低（信息暴露风险）
写入工具数据库增删改、文件写入、邮件发送中（数据损坏风险）
业务操作订单处理、支付调用、审批流程高（直接业务影响）
外部服务第三方API、支付网关、短信服务高（资金/声誉风险）
工具注册协议： 每个工具需要提供标准化的描述（名称、功能描述、参数Schema、返回值类型），以便Agent理解和调用。2026年主流格式是OpenAPI Specification和MCP（Model Context Protocol）。

3.3.7 Layer 7: 模型服务层

核心职责：统一管理所有大模型服务的调用，包括模型路由、Prompt管理、多模型适配和推理加速。 核心功能：
功能说明价值
模型路由根据任务类型自动选择最优模型性价比最大化
Prompt管理Prompt模板、版本管理、A/B测试一致性、可追溯
多模型适配统一接口封装不同厂商的API降低厂商锁定
推理加速批处理、缓存、流式优化降低延迟和成本
降级策略主模型不可用时自动切换备用模型高可用保障

3.3.8 Layer 8: 沙箱执行层

核心职责：为Agent的代码执行和工具调用提供安全隔离环境，防止恶意或错误操作对系统造成损害。
安全红线

Agent具备调用工具和执行代码的能力，如果没有沙箱隔离，可能导致：

  • 数据泄露：Agent读取不应该访问的数据库表
  • 数据破坏：Agent执行了错误的删除操作
  • 资源耗尽：Agent陷入死循环，耗尽CPU/内存
  • 越权操作：Agent以高权限执行了敏感操作
沙箱能力：
  • 进程隔离：每个Agent执行在独立的容器/进程中
  • 网络隔离：限制Agent可访问的网络范围
  • 资源限制：CPU、内存、磁盘、运行时间的上限
  • 权限控制：最小权限原则，只授予必要的操作权限
  • 审计日志：记录所有Agent的操作行为，支持事后追溯
代表方案： E2B沙箱、Docker容器、gVisor安全容器、WebAssembly运行时。

3.3.9 Layer 9: 观测运营层

核心职责：为AI系统提供全方位的监控、度量和运营能力。 观测维度：
维度关键指标工具
性能监控响应延迟、吞吐量、错误率Prometheus、Grafana
成本核算Token消耗、API调用次数、费用分摊LangSmith、自定义仪表盘
质量评估回答准确性、幻觉率、用户满意度RAGAS、TruLens、LLM-as-a-Judge
链路追踪请求在多层架构中的完整执行路径OpenTelemetry、Jaeger
日志管理结构化日志、异常日志、审计日志ELK、Loki

3.4 层间数据流与交互关系

用户 ──请求──▶ [L1入口] ──认证──▶ [L2身份] ──路由──▶ [L3应用]
                                                      │
                                            ──编排──▶ [L4智能体]
                                                      │
                                    ┌────知识检索──▶ [L5知识数据]
                                    │                     │
                                    │    ┌──工具调用──▶ [L6工具业务]
                                    │    │
                                    │    │    ──模型调用──▶ [L7模型服务]
                                    │    │                     │
                                    │    │         ──安全执行──▶ [L8沙箱]
                                    │    │
                                    ▼    ▼
                              [L9观测运营] ←──全层埋点──(日志/指标/追踪)
数据流关键特征：
  1. 自上而下：请求从入口层逐层向下传递，每层进行相应的处理和转换
  2. 跨层调用：Agent编排层可以直接调用知识数据层、工具业务层和模型服务层
  3. 横向观测：观测运营层横切所有层，收集日志、指标和追踪数据
  4. 双向反馈：观测结果可以反馈到上层，用于动态调整策略（如模型路由、限流）

3.5 架构演进路径

架构师建议

不要一开始就搭建完整的九层架构。建议按以下阶段逐步演进：

阶段一：MVP（最小可行产品）

合并L1+L2+L3+L7，直接调用模型API，快速验证场景可行性。核心关注：用户价值验证。

阶段二：知识增强

加入L5知识数据层，实现RAG能力，提升回答准确性。核心关注：准确性和幻觉控制。

阶段三：Agent化

加入L4智能体编排层和L6工具业务层，实现自主任务执行。核心关注：Agent可靠性和安全性。

阶段四：生产化

完善L8沙箱执行层和L9观测运营层，建立安全边界和运维体系。核心关注：稳定性、安全性、成本可控。

阶段五：规模化

完善L2身份权限层的多租户和配额管理，支持大规模用户和业务场景。核心关注：扩展性和运营效率。

3.6 本章小结

九层AI系统架构模型提供了一套系统化的设计框架：

层级核心关键词一句话说明
L1 用户入口交互体验用户与AI对话的界面和渠道
L2 身份权限安全边界谁能用、能用多少、能做什么
L3 AI应用业务价值面向用户的AI功能实现
L4 智能体编排自主执行任务规划、工具路由、多Agent协作
L5 知识数据知识底座向量检索、知识图谱、文档管理
L6 工具业务能力扩展Agent可调用的外部工具和业务API
L7 模型服务模型治理模型路由、Prompt管理、多模型适配
L8 沙箱执行安全隔离Agent操作的安全边界
L9 观测运营可观测性监控、度量、成本、质量

理解这个分层模型，是设计可扩展、可维护、安全的AI系统的基础。下一章将逐层深入，讲解每层的核心组件和技术选型。
