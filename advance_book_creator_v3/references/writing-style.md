# 写作编排规范（writing-style）

> 目的：避免章节编排模板化——读者读到第 3 章就能预测第 4 章每一段的长相，是技术书可读性的最大杀手。
> 本文件只提供编排工具箱和配额约束，不设句式禁令。写作 Agent 每写一章前通读一遍。

## 一、小节编排模式库（相邻小节禁用同一模式）

每个小节从以下模式中选一种编排，**相邻两个小节不得使用同一模式**：

### 1. 叙事型
从事故、场景或历史切入，理论藏在故事后面。
```
（真实场景：一次线上事故/一次踩坑）→ 当时怎么处理的 → 背后是哪个机制 → 正确做法
```
适用：概念引入、最佳实践、反模式。

### 2. 直给型
开门见山先给结论或完整可运行代码，回头解释为什么。
```
（最终配置/代码）→ 逐行解释关键点 → 常见变体 → 什么场景不适用
```
适用：配置指南、API 用法、熟练读者的速查章节。

### 3. 问答型
用一个真实问题驱动全节，问题即标题的展开。
```
（问题：为什么 X 在生产环境总是 Y？）→ 原因拆解 → 解法 → 解法的边界
```
适用：疑难排查、原理机制、FAQ 浓缩。

### 4. 对比型
两个方案正面对垒，用同一组维度打分。
```
（方案 A 是什么、强在哪）→（方案 B 是什么、强在哪）→ 同一场景下的分叉判断 → 选型结论
```
适用：技术选型、易混淆概念辨析。

### 5. 深挖型
一个细节追到底层，不发散。
```
（一个现象/一行配置）→ 往下挖一层 → 再挖一层 → 到读者够用的深度即止
```
适用：核心机制、性能原理、排错根因。

## 二、小节收尾方式轮换

禁止连续两个小节用同一种方式收尾。可用的收尾方式：

1. 提示块收尾（[!TIP]/[!WARN] 等，**全章最多 2-3 个**，见第三节配额）
2. 一句话收尾（一句直接的事实陈述，不加任何修饰）
3. 代码块收尾（以完整可运行的示例结束）
4. 直接过段（不收尾，最后一行内容自然结束，接下一节）
5. 悬念收尾（留一个该节没解决的问题，下一节接住——章节内使用，跨章别用）

## 三、提示块（callout）配额

- **每个 Part 最多 2-3 个**，只放在真正的关键转折或高危警告处
- **禁止每个小节都用要点块收尾**——当每一节都有一个"关键认知"，"关键"就失效了
- 判断标准：删掉这个块，读者会不会漏掉重要信息？不会就不放
- 步骤/对比等结构组件（:::steps / :::compare）不受此配额限制，按内容需要使用
