# adv_book_creator_v3.3 — 目录说明与维护手册

> 深度调研一个主题，生成书籍级 PDF 手册的技能。
> **SKILL.md** 是写书的操作手册（给执行 Agent 看的工作流）；**本文件**是目录导览和维护者须知（这个技能里每个东西是干嘛的、改代码前要知道什么）。
> 技术架构细节见 [DESIGN.md](DESIGN.md)。
>
> **v3.3 相对 v3.2 的核心改动**：① **取消独立"素材采集阶段"**——写作时确需真实事实才现场搜一次、**直接写进正文并加脚注标源**，不再产出 `materials/chapter-{NN}/sNN.md` 素材卡片；② **对抗性审查改为"全书写完统一审一次"**——新起一个审查 Agent（不继承写作上下文）融合双视角（领域主审 + 普通读者），**part 粒度、1-3 个 part/批**，只产出一份全书意见清单 `materials/review/issues.md`，统一修改后逐条核销写 `materials/review/resolved.md`，**只审一次不反复对抗**；③ **术语一致性机械扫描并入 `check-md.js`**（警告级，读 PROJECT.md 术语表禁用同义词列）。构建期 `[0c]` 门禁改为校验 `issues.md` + `resolved.md` 两份留痕存在。
>
> v3.2 相对 v3.1 的三处改动（沿用）：① **素材采集默认不采**（v3.3 起进一步取消该阶段，改为写作时现场搜、直接写正文+脚注）；② 新增**术语纪律**（PROJECT.md 术语表锁定标准译名与禁用同义词）；③ 新增**资深编辑对抗审查**。

## 二、templates/ — 项目骨架源

初始化书项目时由此复制到书项目根。**改这里的文件只影响之后新建的项目**，已存在的书项目用的是各自的副本。

> **防覆盖命名约定**：凡进项目后**不该被覆盖**的项目级数据文件，技能侧一律带 `_template` 后缀——`project_template.md` → 项目 `PROJECT.md`、`version_template.json` → 项目 `version.json`。这样"把新版本技能脚本覆盖进已有项目"时，模板只会落成 `*_template.*`，**不会盖掉项目自己的 `PROJECT.md` / `version.json`**。

| 文件                  | 用途                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `convert-md.js`     | **核心转换器**：Markdown 片段 → HTML 片段。组件语法（\[!TIP] / :::steps / :::compare）在这里解析渲染，占位符零残留断言在这里                |
| `check-md.js`       | **MD 片段门禁**：YAML 完整性、标题层级、禁用 HTML 标签拦截（error 阻断构建）；术语禁用词扫描（TERM001，warning 级不阻断）                                                      |
| `fix-md.js`         | 门禁失败后的自动修复：仅处理标题层级（第X章→h2 等），不碰组件                                                                       |
| `build.js`          | 合并 HTML 片段 → 单文件 HTML（7 套主题 + 导航 + 目录面板），生成 bookmarks.json（含内容指纹）                                       |
| `build-pdf.js`      | PDF 生成：Playwright 测量 + 模拟分页 + pdf-lib 书签。**优先读取 bookmarks.json 缓存，指纹不一致自动重算**                           |
| `build-reader.js`   | 多文件阅读器。**组件样式从 styles.css 按锚点提取**（见维护须知 #2）                                                             |
| `build-md.js`       | Markdown 导出（源头聚合：组件保真/围栏降级/SVG转文字说明+源码框）                     |
| `build-all.js`      | 统一构建入口：门禁（\[0a] MD 源文件 / \[0b] 组件语法 / \[0c] 编辑审查留痕 issues.md+resolved.md）→ 转换 → 按序产出 → 产物完整性检查                                                              |
| `styles.css`        | 全部样式。**组件样式的唯一来源**（高亮块/对比块/步骤卡片/图片组件四段，build-reader 构建期提取）                                              |
| `epub-styles.css`   | EPUB 专用样式，**独立维护**（阅读设备兼容差异大，不参与组件样式单一来源）                                                               |
| `build-epub-pro.js` | EPUB 精排生成器（依赖可选的 highlight.js / archiver）                                                               |
| `lib/fence-scan.js` | **共享围栏状态机**：代码围栏（\`\`\` / \~\~\~）判定的唯一实现。convert-md、check-md、build-all 三方共用，防止各写一套判定逻辑漂移（曾导致配对错位吞掉半章正文） |
| `lib/footnote-pop.js` | **脚注点击弹层**：点击正文脚注标记在标记旁浮出内容（替代跳转章末）。build.js 与 build-reader.js 构建期内联的**单一来源**；样式在 styles.css「脚注」段。EPUB 不用它（多看自有弹窗） |
| `project_template.md` | **项目中枢模板**：init 读取 → 把 `{{书名}}` 替换为书名 → 生成项目根 `PROJECT.md`（带 `_template` 后缀，防覆盖项目文件） |
| `version_template.json` | **版本信息模板**：init 读取 → 注入 title/lastUpdate → 生成项目根 `version.json`（带 `_template` 后缀，防覆盖项目文件） |

## 五、写作质量三道防线（v3.2 起；审查在 v3.3 改为全书写完统一审一次）

> v3.2 把"写好书"拆成三道防线：**编排（治机械感）→ 术语（治生造词）→ 编辑审查（治生硬/空话/整体质量）**。三者分工不重叠。

### 第一道：写作编排机制（治"机械感"）

> 背景：实际成书中每个小节都是"设问开头 → 枚举 → 要点块收尾"的同一模板，且几乎每节都有一个"关键认知"提示块（强调块通胀）。规范文件：[references/writing-style.md](references/writing-style.md)。

三条核心规则（写作 Agent 每章开工前必须执行）：

1. **编排模式轮换**：每节从 5 种模式中选一种编排——叙事型（场景切入）/ 直给型（先代码后解释）/ 问答型（问题驱动）/ 对比型（方案对垒）/ 深挖型（单点追到底）。**相邻小节不得用同一模式**。
2. **收尾方式轮换**：提示块 / 一句话 / 代码块 / 直接过段 / 章内悬念，5 种轮着来，禁止连续两节同款。
3. **提示块配额上限**：每个 Part **最多 2-3 个**（只放真正的关键转折或高危警告），**禁止每个小节都用要点块收尾**。判断标准：删掉这个块，读者会不会漏掉重要信息？不会就不放。

注意与旧版"去 AI 腔规范"的区别：那是一份句式禁令清单（已被移除，实测无效）；这套是**强制决策点**——模型写每节前必须显式选择编排模式，选型本身就会改变写法。check-md 门禁**不检测**文风类问题（门禁只管语法准确性）。

### 第二道：术语纪律（治"生造词"）

> 背景：AI 写书时会"解释性改写"，把行业标准术语自造成近义白话（CDC→"抓变化"、Kafka→"管道"）。不算错，但出戏，懂行的读者立刻觉得不专业。规范文件：[references/terminology-discipline.md](references/terminology-discipline.md)。

- **先定书籍类型**：PROJECT.md 五档选一（技术/方法技艺/商业/人文/科普）——它决定"什么算标准词"
- **术语表锁定**：规划阶段建表（中文标准名 / 英文 / 全称 / 首次出现章 / **禁用同义词**），用户确认后锁定
- **三条硬规则**：领域通用词优先（不自造）；首次出现给足信息；同一概念全书同一词
- **按体裁变形态**：技术/科普给中英对照；方法/技艺存学科通用概念（写作书："叙述视角"不写"看事情的框框"）；人文/叙事改"用词台账"（只钉人名地名）
- **禁用同义词列**是把 AI 易自造的说法钉死（如"抓变化、管道"）——写作 Agent 见到列内词一律禁用
- **执行分两层**：①机械层——`check-md.js` 扫片段是否出现术语表「禁用同义词」列里的词（TERM001，**警告级**，机械子串匹配可能有误报、不阻断构建）；②语义层——资深编辑审查抓表外新造词与术语准确性。**边界**：机械层只能抓已登记的禁词，表外新造词靠审查 Agent 兜底

### 第三道：对抗性编辑审查（治"生硬/空话/整体质量"）

> 背景：写作 Agent 是作者，天然宽容自己的稿子。审查交给**独立子 Agent**（新起、不继承写作上下文），用对抗姿态挑毛病；**v3.3 把审查改为"全书写完统一审一次"**。规范文件：[references/editor-review.md](references/editor-review.md)。

- **只审一次、全书写完再审**：写作中途不审；全文封笔后派一个审查 Agent 统一审一遍——审查 → 落盘清单 → 统一修改 → 核销，结束，**不反复对抗**
- **一个 Agent 融合双视角**：领域主审（身份由 PROJECT.md「对抗性审查设计」定：技术编辑/业务专家/科普编辑/学术编辑/文学编辑…）+ 普通读者；**两视角各独立走一遍清单**（防止读者视角被专家视角淹没）
- **提示词装配（干净上下文）**：审查 Agent 是新会话、必须自带上下文——取 `references/editor-review.md`「审查 Agent 提示词模板」，填入 PROJECT.md「九、对抗性审查设计」的主审身份/粒度 → 粘给它；**只给规格文件与产物，不粘写作过程/作者自评**（否则锚定审查者）。模板只此一份，不在 PROJECT.md 再抄
- **粒度 = part**：计划里合成 part 的按 part 审，否则逐章；**不做跨 part 交叉分析**（连贯性交给规划阶段的 PROJECT.md/Mini-Plan）。批次：1 个 Agent 处理 1-3 个 part，**禁止每 part 派一个 Agent**
- **只落盘不改稿**：审查只产出全书意见清单 `materials/review/issues.md`（按 part 分节；章节 | 级别 | 类型 | 原句 | 建议）——审查阶段不动稿
- **统一修改 + 逐条核销**：审查完成后统一改一次，再逐条核销写 `materials/review/resolved.md`（`#N 已改` / `驳回：理由`）；核销是极轻收尾校验，只读被改的句子，不重扫全文
- **必须给证据**：每条问题引原句（≤30 字）+ 类型 + 改写建议；**禁止为凑数编问题**
- **不误伤体裁**：文学里正当的修辞/节奏不可当 AI 腔误杀
- **构建期真门禁**：`build-all.js` 的 `[0c]` 校验 `materials/review/issues.md` 与 `resolved.md` 是否存在，**缺任一份直接拒绝构建**（仅校验留痕存在，不判断内容质量；预览可用 `--no-gate` 跳过）
- **与门禁分工**：编辑审**语义**（术语/文风/稻草人），check-md 管**语法**（YAML/标题/HTML + 术语禁用词扫描），`build-all [0c]` 管**留痕**，三道都要过、互不替代

> **双视角清单**：专家视角=生造名词/术语准确性 · 专业结论正确性 · 时效 · 逻辑自洽 · 案例真实性；读者视角=语句生硬/AI腔 · 空话 · 稻草人（作者捏造读者误解来纠正）· 读不懂/缺前置 · 啰嗦。**不再有独立的"去 AI 味"流程**，统一并入本审查。

## 维护须知（改代码前必读，均为实际踩坑沉淀）

1. **lib/ 下的共享依赖**（fence-scan.js / cover-select.js / footnote-pop.js / hljs 的 bundle）：init 会复制到每个书项目的 `lib/`。修改它们后，已存在的书项目不会自动更新，需要手动同步或重建项目。尤其 `footnote-pop.js` 被 build.js 与 build-reader.js 同时内联——**要改就改这一份，别在任一构建脚本里再抄一份**。
2. **组件样式只改 styles.css**：阅读器构建时按四个段落锚点（`高亮块/信息块`、`对比示例块`、`简洁步骤卡片`、`图片组件`）从 styles.css 提取，删改段落标题注释会导致提取失败（有警告）。EPUB 的 epub-styles.css 例外，独立维护。
3. **禁用 HTML 清单有三份**：check-md.js（TAG001）、build-all.js（内置门禁）、migrate-to-lite.js（残留检查）。**以 check-md 为权威源**，改清单必须三处同步——漏同步的后果：门禁放行但迁移报警，或反之。
4. **figure/svg 必须闭合**：未闭合的 figure 会让后续内容继承其样式（曾导致整章居中）。convert-md 有自愈（自动补 `</figure>` + 警告），styles.css 也做了不可继承化防御，但写对才是正道。
5. **占位符零残留是硬断言**：convert-md 输出中若残留 `__XXX_N__` 占位符会直接终止构建。若触发，说明转换逻辑有 bug 或片段内容异常，不要绕过，先修根因。
6. **"不是…而是…"对比句式**：AI 写作的高频单调句式（某书 119 节命中 117 次）。当前未设约束（用户决策）；如需管控，check-md 加密度检查（命中数/章节标题数 > 阈值即 warning）即可，检测正则见本技能会话中的扫描脚本模式。
7. **PDF 的 playwright 依赖**：全局安装时构建前需 `$env:NODE_PATH = (npm root -g)`；HTML/阅读器/MD 三种产物无此依赖。
