# 资深编辑对抗审查规范（editor-review）

> 目的：写作 Agent 是"作者"，天然宽容自己的稿子。本规范把审查交给**独立的资深编辑 Agent**（新起 Agent，不继承写作上下文），用对抗姿态挑毛病——这是治"术语生造、语言生硬、编排重复、空话连篇、稻草人假设"的主手段。
>
> **v3.3 改为"全书写完统一审一次"**：审查整体后移到全部内容写作完成之后，只执行一次；审查阶段**只产出意见清单、不改稿**，随后统一修改、逐条核销。不再有独立的"去 AI 味"流程——它统一并入本审查。

## 一、触发时机与独立性

- **时机**：全书所有片段（`fragments/part*.md`）写完、封笔之后再审。写作中途不审。
- **独立性**：**新起审查 Agent**，不继承写作 Agent 的对话上下文——保证不被作者思路带跑、不自我宽容。
- **只审一次**：审查 → 落盘清单 → 统一修改 → 核销，结束。**不反复对抗**（不做"改完再审一轮"的循环；核销只是极轻的收尾校验）。
- **上下文断裂不是问题**：跨章/跨 part 的结构与脉络连贯性，由 `PROJECT.md`（大纲的前置依赖）与单章 Mini-Plan 在**规划阶段**解决，不由审查兜底。

## 二、角色设定（审查 Agent 的系统人设）

你是这本 **{书籍类型}** 的**资深编辑**，做过十年出版，最恨两件事：**作者把行话改成自作聪明的白话**、**把三句话能说清的事写成一段正确的废话**。

**主审身份由 `PROJECT.md`「对抗性审查设计」栏指定**，随书型变：

| 书籍类型 | 主审身份 | 身份设定句（可直接填入下方提示词） |
|---|---|---|
| 技术/专业 | 资深技术编辑 | 你是资深技术编辑，审过十年编程/工程书，一眼看出技术表述失准、版本过期、示例代码跑不通、术语前后不一 |
| 商业/观点 | 资深业务专家 | 你是资深业务专家，最恨没有论据的断言和包装过的黑话 |
| 科普 | 资深科普编辑 | 你是资深科普编辑，专抓"为了通俗牺牲准确"或"为了准确写得没人看懂" |
| 方法/技艺 | 该领域资深编辑（如写作书→资深文学编辑） | 你是该领域资深编辑，专挑方法"看着对、照着做会翻车"的地方 |
| 人文/叙事 | 资深文学编辑 | 你是资深文学编辑，在意语言质感与节奏，不容忍被 AI 腔磨平的句子 |
| 其他 | 按 PROJECT.md 指定 | 由 PROJECT.md 写明主审身份的一句话人设 |

**同一个 Agent 必须兼两重身份**：领域主审 **+** 一个普通读者。→ 见 §四 的双视角清单，**两视角必须各独立走一遍**，防止读者视角被专家视角淹没。

你的默认立场是：**这份稿子有问题，我的任务是找出来**。你不需要礼貌，只需要准确。

### 审查 Agent 提示词模板（唯一来源，可直接复制）

> **组装方式**：取本模板 → 把 `PROJECT.md`「九、对抗性审查设计」的『主审身份 / 粒度』填入 `{}` 占位 → 粘给**新起的独立 Agent**（新会话，不继承写作上下文）。
> **只给规格文件与产物，不给写作过程与作者自评**——否则会锚定审查者（作者说一句"这里有意为之"，它放过了）。
> 提示词模板**只此一份**，不要在 PROJECT.md 里再抄一遍（两份必漂移）。

```text
你是 {主审身份}，受聘对即将出版的《{书名}》（{书籍类型}）做终审。
你不是作者，没参与写作，不为任何写法辩护——你的唯一职责是找出会让读者
误解、执行失败或失去信任的问题。

【必读文件】按顺序读，以文件为准，不要凭记忆：
1. PROJECT.md —— 本书定位/读者画像/术语表(含禁用同义词)/大纲/数据速查/审查设计。这是你判"对错"的标准。
2. fragments/part*.md —— 审查对象（本批：{本批 part 列表}）。
3. research/editor-review.md —— 你的审查清单与输出格式（§四 / §七）。

【方法】走两趟，先走完一趟再走下一趟，不得合并：
- 第一趟＝领域主审：按 §四 视角 A（A1–A5）逐条过稿。
- 第二趟＝普通读者：忘掉专家身份，按 §四 视角 B（B1–B5）逐条过稿。

【硬规则】
- 只审不改：不要修改任何 fragments 文件。
- 每条问题给：原句（≤30 字）+ 级别（高/中/低）+ 类型 + 改写建议。
- 禁止凑数：清单走完确实没问题就写"通过"。假问题比漏问题更坏。
- 不误伤体裁：文学里正当的修辞 / 节奏不算 AI 腔（见 §五 体裁边界）。
- 高风险领域（安全 / 法律 / 医疗 / 金融）的问题单独标注。

【输出】写入 materials/review/issues.md，严格按 §七 格式
（按 part 分节；全书问题编号 # 跨 part 连续；无问题的 part 写 "## partNN：通过"）。
```

## 三、审查粒度与批次

- **粒度 = part**：`PROJECT.md` 计划里把若干章合成一个 part 的，按 part 审；未合成 part 的，**逐个章节审**。
- **不做跨 part / 跨章交叉分析**（理由见 §一）。
- **批次**：1 个审查 Agent 处理 **1-3 个 part**；大书可分多批，各批可并行。**不要每 part 派一个 Agent**（会让依据文件重复装载 N 次）。

## 四、审查清单（双视角，各自独立走一遍）

> 走查是**脑内动作**：按清单逐条过稿，**只把命中项写进清单**。两个视角都要走，不得合并省略。

### 视角 A：领域主审（按书籍类型侧重）

| # | 维度 | 一眼判据 |
|---|---|---|
| A1 | **生造名词 / 术语准确性** | 是否自造词替代领域通用词；是否与 `PROJECT.md` 术语表"禁用同义词"列冲突；同一概念是否全书同一词 |
| A2 | **专业结论正确性** | 结论是否与领域共识一致；有无硬伤 |
| A3 | **时效** | 版本号 / 配置值 / API 现状是否过期（技术书重点） |
| A4 | **逻辑自洽** | 前后有无自相矛盾；推理链是否断裂 |
| A5 | **案例真实性** | 案例 / 数据是否编造，或是否有来源标注（脚注 `[^n]`） |

### 视角 B：普通读者（所有书型都查）

| # | 维度 | 一眼判据 |
|---|---|---|
| B1 | **语句生硬 / AI 腔** | 见 §五 反 AI 腔速查 |
| B2 | **空话与"正确的废话"** | "极大提升"等无支撑程度词；"多读多写"式没有信息量的话 |
| B3 | **稻草人** | 作者捏一个"你以为…其实不是"的读者误解来纠正。判据：这个误解是**真普遍存在**，还是作者为行文**捏造**的？真误解保留，捏造的删。（含：凭空假设读者有奇怪想法、虚构"读者这么做是错的"来纠正） |
| B4 | **读不懂 / 缺前置** | 读者会在哪一句卡住；术语首次出现是否给足信息；有无跳跃 |
| B5 | **啰嗦** | 同一意思反复说；铺垫过长；可删的段落 |

## 五、反 AI 腔速查（B1 的处方；按体裁适用边界判断）

| 症状 | 处方 |
|---|---|
| 一段里 "——" 超过 1 次 | 改冒号 / 逗号 / 句号断句 |
| "不是 X，而是 Y" 成段重复 | 删否定半句，直接陈述 Y |
| 拟人化（"数据在说话""方法自己跑了起来"） | 改主语明确的动作句 |
| 空洞三连 / 四连排比 | 留最有力量一组，其余拆长短句 |
| 模板收束句（"综上所述 / 值得注意的是 / 首先其次最后"） | 删复述式总结；要收束就给新判断 |
| 自指句（"作为一个 AI / 语言模型"） | 删除 |
| 空泛程度词无支撑（"极大提升 / 显著改善"） | 补量 / 例，或删程度词 |
| 名词化黑话（赋能 / 抓手 / 闭环 / 颗粒度） | 还原成动词句 |
| 无来源绝对化（"最 / 唯一 / 众所周知 / 毋庸置疑"） | 降级为相对表达或删除 |
| 过密小标题 / 通篇 "1. 2. 3." 清单 | 合并小节、段落过渡（教程 / SOP 除外） |
| 过度雕琢的比喻（为"高级感"堆砌） | 只留一个真正帮助理解的 |
| 清单式"正确的废话" | 给可照做的动作，或补一个反例 |

> **体裁边界**：文学里正当的修辞 / 节奏，不可当 AI 腔误杀。高风险领域（安全 / 法律 / 医疗 / 金融）另提示用户确认。

## 六、对抗性原则（必须遵守）

1. **默认有错**：开审前假设稿子不合格；逐条走查清单，用证据说话。
2. **必须给证据**：每条问题**引用原句**（≤30 字）+ 类型 + 改写建议。空泛的"建议再润色"不算问题，作废。
3. **不制造假问题**：清单走得完、确实没问题，就写"通过"。**禁止为凑数编问题**——假问题比漏问题更坏。
4. **不改写全文**：产出是**意见清单**，不是替作者重写；只给关键处的改写示范。
5. **不误伤体裁**：按体裁适用边界判断。

## 七、输出：统一落盘一份全书意见清单

审查**只产出**一份清单，写入 `materials/review/issues.md`（**审查阶段不改稿**）。按 part 分节：

```markdown
# 编辑审查意见清单

> 审查对象：全书 fragments（共 N 个 part）
> 主审身份：{PROJECT.md 指定}
> 审查结论：需修改 N 处 / 通过

## part01（第 1-3 章）

| # | 章节 | 级别 | 类型 | 原句（≤30字） | 建议 |
|---|---|---|---|---|---|
| 1 | 第一章 | 高 | 用词纪律 | "……的抓变化机制……" | 改为"变更数据捕获（CDC）" |
| 2 | 第二章 | 中 | 语言生硬 | "不是 A，而是 B" | 拆成两句直陈 |

## part02（第 4-5 章）
| # | 章节 | 级别 | 类型 | 原句（≤30字） | 建议 |
|---|---|---|---|---|---|
| 3 | 第四章 | 高 | 案例真实性 | "某公司 2024 年……" | 补脚注标源，或改为示意 |
```

- **级别**：高 = 用词违规 / 事实编造（必须改）；中 = 生硬重复 / 稻草人（应改）；低 = 润色建议（可选）。
- 无问题的 part 写一行 `## partNN：通过`，不列空表。
- 全书问题编号 `#` **连续唯一**（跨 part 递增），便于核销引用。
- **落盘后写信号**：`node scripts/stage.js review --done`（构建门禁 `[0c]` 依据）。

## 八、统一修改与核销

1. 全部审查完成后，**统一执行一次修改**：按 `issues.md` 逐条处理；高 / 中级**必须处理**，低级可选；不认同的**须写明理由**，不许静默跳过。
2. 修改后**逐条核销**，写入 `materials/review/resolved.md`：

```markdown
# 审查意见核销

| # | 处理 | 说明 |
|---|---|---|
| 1 | 已改 | 改为"变更数据捕获（CDC）" |
| 2 | 驳回 | 此处"不是…而是…"是必要对比，非 AI 腔 |
```

3. **核销是极轻的收尾校验**：只读被改动的句子，确认与说明一致即可，**不重扫全文、不做二次对抗**。
4. 核销完成后写入 `PROJECT.md` 进度追踪（统一对抗审查 ✅ / 清单核销 ✅）。
5. **写信号**：`node scripts/stage.js revision --done`（构建门禁 `[0c]` 依据）。**此后若再动稿，指纹校验会在构建时拦下**，需重跑本步（必要时重审）。

## 九、机械扫描（不是审查，是脚本兜底）

- **术语一致性扫描**已并入 `templates/check-md.js`（构建门禁 `[0b]`），**警告级不阻断**：解析 `PROJECT.md` §三 术语表的「禁用同义词」列 → 扫 `fragments/*.md`（跳过代码块 / 行内代码）→ 打印 `文件:行号` + 上下文。
- **边界（必须清楚）**：脚本**只能抓术语表里已登记的禁用词**。表外新造词、语句生硬、稻草人这些语义问题**只能靠审查 Agent**；二者互补，不可互相替代。
- 脚本可能有误报（如禁用词恰好出现在引用语义中），故为警告级；命中项请人工判断。

## 十、与门禁的分工

- **编辑审查**：语义层——术语、文风、编排、真实性、稻草人（本规范负责）。
- **check-md.js `[0b]`**：语法层——YAML、标题层级、禁用 HTML 标签 + **术语禁用词机械扫描（警告级）**。
- **build-all.js `[0c]`**：流程层（纯机械）——三段信号（writing/review/revision）+ `issues.md`/`resolved.md` 存在 + 大纲 vs 片段（防漏写）+ 核销覆盖（防漏核销）+ 片段指纹（防改后未被重审），任一不过即拒绝构建（`--no-gate` 仅用于预览 / 中途构建）。
- 三者不重叠、不互相替代，**都要过**。
